What the assistant sees, keeps and looks up

Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status from one visit to the next. Those are two different memory problems, and the model's budget pays for both. At your design review you will need to say what you keep in context, what you save, and how you find a page, and give a reason for each.

Why the assistant needs a memory plan O3 2 min

Picture a mechanic's bench. Only so many tools fit within arm's reach. Put every wrench you own on it and you spend the job digging for the 10 mm socket; put the right six there and the work flows. The rest of your tools sit in the toolbox, the service manual sits on a shelf, and the customer's maintenance logbook sits in a folder at the front desk. Nobody expects the bench to hold the whole shop.

An agent has the same problem. What the model can use right now is small. What it could look up is huge. What it must remember for next time has to be written somewhere that survives the end of the conversation. Your makerspace assistant faces all three at once:

  • Right now: the student's question and the results of the tools it has called in this request.
  • Look up: hundreds of pages of machine manuals, far more than it should read for any one question.
  • For next time: which machines this student has been trained on.

This lesson takes those three in turn, with one demo you play with and two pictures.

Warm-up: the loop, revisited O1 3 min

Before anything new, pull the agent loop out of your head, because everything below hangs on it. Try this without scrolling up.

Recall

The assistant gets "Is the laser cutter free on Friday?" and asks for the calendar tool. The program runs the tool and has the result. What happens next, and how many separate times has the model been called by the time it writes the final answer?

Check your answer

The program, not the model, runs the tool. It then puts the result back in front of the model and calls the model again; the loop repeats until the model writes a final answer instead of asking for another action. In the simplest case that is two calls: one that ends in the tool request, and a second that reads the result and answers. Every step is a separate model call.

The connection to today: a separate call means the model remembers nothing from the previous call by itself. Each call receives the text so far, and that text is the context: everything the model is shown for one call. The question this lesson answers is what the program chooses to put in it.

Recall, second question

Say the model has just asked for search_manuals and the program has run it. Name two things the program puts into the text for the model's next call, and say who decided to run the tool.

Check your answer

The program puts in the earlier text (the student's question and the model's own request) and the new tool result, so the model can read what came back. The program decided to run the tool, not the model: the model only wrote a request naming it. This is the whole reason context is a design choice. The model sees what the program hands it, and nothing else, so your program chooses what gets handed over.

The context window and what stays between steps O3 7 min

The context window is the limit on how much text the model can be given in one call. Text is counted in tokens, the small pieces of text a model reads and writes (the unit from the first lesson on what a model does); a window is a number of tokens. That is the first fact. The second matters more for design: a window that has room is not the same as a window that works well.

Anthropic's engineering team describes context as a finite resource: every token you add draws on the model's attention (how it weighs every token in the window against the others, so more tokens means less weight on each), and the resulting decline is called context rot: as the number of tokens in the window grows, the model's ability to recall information from within it gets worse, in all models, though some degrade more gently than others (Effective context engineering for AI agents). The practical rule they draw is to find the smallest set of high-signal tokens that makes the result you want likely.

What stays between steps

Because every step is a separate call, "staying" means the program puts it back into the next call. In an agent loop the default is that everything stays: the task, the model's own requests, and each tool's result are all appended to the context and sent again at every step. So every tool result you add is paid for again at every later step, in room, in attention and in tokens billed. That is why your small budget makes this a cost question as well as a quality question.

That growth is what the article means by context being a finite resource. Two moves keep a long run manageable, both described in Effective context engineering for AI agents:

  • Clearing old tool results. Once a raw result deep in the history has been used, the program can drop it. The decision that came from it stays in the model's own messages; the bulk of the data goes.
  • Compaction. When the window nears its limit, the program asks the model to summarize the work so far and starts a new window from the task plus that summary. The risk is a summary that leaves out the one detail you needed.

Figure 1 shows one run. Notice how the bar at step 4 is almost full, and how the two fixes end very differently: clearing keeps the newest result untouched, while compaction keeps only a short summary of everything. Now do it yourself.

Demo O3 5 min

Work through the three prompts under the demo in order. They take about five minutes. Predict before you press, because the prediction is what makes the result stick.

Fill the window, then decide

The assistant is booking the laser cutter and looking up a 3 mm acrylic setting. Press Next step and watch each tool result take room. Sizes, and the 50 and 80 thresholds in the status line, are examples.

    1. Before pressing Next step: after step 4, how full will the window be? Then check.
    2. Press Start over, then Paste in the whole manual before any step. Does more text help? What does the readout say?
    3. Press Start over and Next step four times. When step 5 will not fit, try clear, compact and save a note. What does each remove, and what does each keep?

    What you should have seen: step 4 left the window at 91 of 100 units, so step 5 would not fit until you cleared or compacted. Clearing left 27 units and compaction left 25, so both freed most of the room; the difference is what they kept. Clearing kept the newest result whole and dropped everything else, while compaction kept a short gist of all of it. A saved note freed nothing in the window, because notes live outside it. And pasting in the whole manual made things worse, not better.

    A common mix-up

    "A bigger window means I can just put everything in." It is tempting because more information feels safer, and a long prompt feels thorough. But the source above is explicit that tokens are a budget with diminishing returns: as the window grows, the model's recall of its contents declines (Anthropic). In the demo the pasted manual took 60 of your 100 units, and the readout warned that it spreads attention thin. Aim for the smallest set that makes the right answer likely.

    Check yourself

    A student has made six tool calls in one long booking chat. The assistant starts missing details from the first calendar result. Which fix matches the cause?

    Show the answer

    Clear used results or compact the history. The problem is a crowded window, so the cure is a smaller, higher-signal one.

    Memory between sessions: notes O3 5 min

    Everything so far lives inside one session. When it ends, the window is gone. The model's own knowledge does not change either, since its training data stops at some point (that is the outdated-fact problem you spotted in the first lesson). So how does the assistant know next week that Riley finished the laser cutter training?

    The answer: it writes it down. The approach Anthropic calls structured note-taking, or agentic memory, has the agent write notes to storage outside the context window and pull them back in at later times (Effective context engineering for AI agents). The model is not remembering; the program saves text and loads it into the next session's context.

    Think of the maintenance logbook in a car's glovebox. The car does not remember its last oil change. The record does, and a mechanic who opens it knows where to start. The log has to be written at the time, and someone has to open it.

    Two kinds of note for your assistant

    • Per-student records. A small structured file or database row per student: machines trained on, date, any restrictions. A tool such as check_training_record(student) reads it. This is the training-status memory your mission needs.
    • Working notes. What the agent wrote to itself mid-task, such as "waiting on the student to pick a time". Saving this before a long run is compacted means the detail survives the summary. That is why the demo's "Save a note" button took no room in the window.

    Notice the design decisions this forces. What deserves a note? Who may write it: the model, or only the program after a trusted check such as a staff sign-off? And when does it get loaded: always, or only when a student's name comes up? Loading a note costs tokens like anything else, so a record should be loaded for the student in front of you, not all of them.

    Trace one case. On Monday a student finishes laser cutter training with a staff member. The staff tool calls save_record, and the program writes a line such as "student 4417: laser cutter, trained, Monday" to the record store. Monday's window is then discarded. On Thursday the same student starts a new chat. The program looks up record 4417 before the first model call and places that one line in the window with the question. When the student asks to book the laser cutter, the model can see the training line and proceed. The model never "remembered" anything: the line was written, kept, found and loaded, and every one of those four steps is code you will write or choose.

    A short procedure for adding memory to your assistant, in the order the program does it:

    1. Decide the trigger. Write a note when something changes that a later session will need: a training sign-off, a booking, a stated preference. Do not log every chat line; a long log is just a long window waiting to happen.
    2. Write it somewhere that survives. A file or database the program owns, keyed by the student, in a fixed shape so it is easy to read back.
    3. Load it at the start of the next session. Look the record up by who is asking, and place it in the context before the model's first call.
    4. Keep it short enough to be worth loading. If a record grows, summarize the old part the way compaction does, so it still costs little each time.

    A common mix-up

    "The assistant remembers me from last visit." It feels natural because a chat looks like a continuing conversation. In fact each session starts with an empty window, and only what was written down and reloaded is remembered. If the program never saved your training status, or never loads it, the assistant has no idea who you are, however friendly the last chat was.

    Check yourself

    On Monday a student finishes band saw training in chat. On Thursday a new session starts and the assistant says no training is on file. What most likely went wrong?

    Show the answer

    Nothing saved the record, or nothing loaded it. Memory between sessions is a save step and a load step in your program, not a property of the model.

    Retrieval: finding the right manual page O3 6 min

    The manuals are the third problem. A bench cannot hold the shop, so the assistant needs a way to fetch just the page it needs.

    First, a check on whether you need anything clever at all. Anthropic notes that if your knowledge base is smaller than about 200,000 tokens, roughly 500 pages, you can simply include the whole thing in the prompt (Introducing Contextual Retrieval). Count your manuals first. But remember the demo: even when it fits, filling the window with it is not free in cost or in attention.

    Past that size you need retrieval: finding the few passages relevant to a question and putting only those in the context. The standard recipe from the same article is to split each document into chunks of no more than a few hundred tokens, then search the chunks for the ones that match the question.

    Figure 2 is the whole idea. It is the index at the back of a book, automated: you do not read the whole book to find a topic, you look it up and open the two pages it points to. How does the search decide what matches? Two methods, and they fail in opposite ways (Introducing Contextual Retrieval):

    • Embeddings turn text into numbers that capture meaning, so "settings for thin clear plastic" can match a chunk about acrylic even though the words differ. They can miss exact identifiers.
    • BM25 matches exact words and phrases. A query for an error code like "TS-999" finds the chunk that contains "TS-999", where an embedding may return something merely related. It knows nothing of synonyms.

    The article's advice is to use both together, which suits a manual full of both plain descriptions and error codes. Its refined version of this search cut the share of failed top-20 retrievals from 5.7% to 2.9%; you will meet the details in Go further. The lesson to take now is that how you retrieve is a design choice with measurable results.

    Putting retrieval in the loop you already know, one request looks like this:

    1. The student asks about 3 mm acrylic.
    2. The model requests a search_manuals tool call with a short query.
    3. The program runs the search over the chunks, with the hybrid method, and returns the top few.
    4. Those chunks go into the context as the tool result, and the model is called again to write the answer from them.

    So retrieval is not a new kind of machinery. It is a tool, and its result is one more item in the window, with all the costs you just watched in the demo. That is also why the number of chunks you return matters: too few and the answer may be missing, too many and you are back to pasting in the manual. Choosing those numbers well is next lesson's work.

    A chunk of a few hundred tokens is about one thing, so it either answers the question or clearly does not. Cut a manual badly, though, and a chunk can lose what it refers to, for instance a paragraph that says "it" without saying which machine. That weakness is a good reason to test retrieval on real student questions before trusting it.

    The agent can also look things up as it goes, keeping lightweight references and loading content only when needed, which is slower but keeps the window lean (Anthropic).

    Next lesson territory: how big to make chunks, how to rank the results, and what each call costs in dollars. For now, hold the shape: split, match, load only the best.

    A student types "error E-417" into the assistant. Which search is most likely to find the right manual chunk, and why?

    BM25: it matches the exact code. A hybrid of BM25 and embeddings is the safer design, since students will phrase some questions loosely and others by code.

    Worked example and practice O3 4 min

    Worked example

    A student writes: "Book me the laser cutter Friday afternoon, and what setting should I use for 3 mm acrylic?" Sort what the assistant needs into three places.

    1. Start with what must be in the window now. The student's message, the instructions on how to behave, and the tool descriptions. Without these the model cannot act at all. They are small and needed at every step.
    2. Next, what comes from notes. Whether this student is trained on the laser cutter. Booking depends on it, and it persists between visits, so it comes from the per-student record. Load that one record into the window, not all of them.
    3. Then, what is retrieved on demand. The acrylic setting lives somewhere in the laser cutter manual. Search the chunks, load the best one or two, and leave the rest of the manual in storage.
    4. Finally, what is cleared or kept short. The calendar tool might return a whole week of bookings. Once the Friday slot is found, the raw week can be cleared. After booking, write one new note: "booked, Friday 2 pm."
    Your turn

    A different student asks: "Am I cleared for the 3D printer, and what does the error E-417 mean?" Decide where each of these lives: the question itself, the student's training status, the explanation of E-417, and the printer's full 120-page manual. The first step is given: the question itself goes in the window now. Do the other three before opening the solution.

    Show a solution

    Training status: a note, saved in an earlier session, read by a tool for this student and loaded into the window. E-417: retrieved on demand, using an exact-term search, since it is a code. Load only that chunk. The 120-page manual: stays in storage; only the chunk that came back from the search enters the window. Never paste it whole.

    A second worked example

    A student writes: "Cancel my Friday booking." The same three places, applied again.

    1. In the window now: the request, the instructions and the tool descriptions, as before. They are always needed.
    2. From notes: which booking is this student's. The program looks up this student's record and loads only their bookings, because the model cannot cancel what it cannot see, and loading every student's bookings would waste room.
    3. Retrieved: possibly the cancellation policy from the booking manual, such as how much notice is needed. Search for it; do not paste in the manual.
    4. After the action: the cancellation tool's result is one short item in the window. Write a new note that the booking was cancelled, so the next session does not offer a slot that is already gone.

    Notice that the model's job is the same in both examples; only what the program hands it differs.

    One more case, because the worst design mistakes hide in the details. The team proposes: "At the start of every session, load every student's record, so the assistant is always ready." Think about what that does to the window, to the bill and to the attention budget, before you pick below.

    Check yourself

    What is the main problem with loading every student's record at the start of each session?

    Show the answer

    It fills the window with irrelevant text. Look up and load only the record of the student who is asking.

    Summary O3 1.5 min

    • The context is everything the model sees in one call. It is limited, and a fuller window is not a better one: keep the smallest high-signal set, and clear or compact when it crowds.
    • Nothing carries over between sessions unless the program writes it down and loads it again. Notes are that save-and-load step.
    • Retrieval splits long documents into chunks, matches the question, and loads only the best ones; embeddings find meaning, BM25 finds exact terms.

    Say it in your own words: without looking up, explain to a teammate where the assistant keeps the student's question, the student's training status, and the laser cutter manual, and why each lives there.
