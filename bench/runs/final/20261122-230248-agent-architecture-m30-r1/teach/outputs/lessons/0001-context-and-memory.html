Why the assistant must remember O3 2 min

Picture a student walking up to the makerspace kiosk on Tuesday and asking, "Can I book the 3D printer on Friday?" To answer well, the assistant needs three different kinds of information, and they live in three different places.

  • What is happening right now: the question, the calendar result it just fetched, the step it is on.
  • What is true about this student from earlier visits: they finished the printer training two weeks ago.
  • What is written in a long document: the printer's manual, with the rules about bed temperature and filament.

If you put all three in one place, you get a bad design: either the manual crowds out everything else, or the student's status is lost the moment the chat ends. Good design keeps each kind of information where it belongs, and moves only what is needed into the model's view at the right moment.

A car has the same split. The engine does the work in the moment and holds only what is happening now: rpm, temperature, the fuel in the cylinders. The logbook in the glovebox records past service, so the next mechanic does not have to guess. The shop manual sits on a shelf, and nobody reads all of it to change one oil filter; they turn to the right page. For an agent, the engine is the context window, the logbook is notes, and the shop manual is reached by retrieval. This lesson takes them one at a time.

The language model underneath knows only what it learned in training plus the text it is given on each call (learning record 0001). So everything in this lesson is a decision about which text to hand it, and when.

The model asks for an action, such as a call to the booking-calendar tool with the date. The program around the model runs that tool, not the model. The result is sent back to the model on a new call, and the loop repeats until the model writes a final answer such as "Yes, from 2 pm." Every step is a separate model call. That detail is today's starting point: if each step is a separate call, then what the model "knows" at step three is only what the program chose to send it at step three.

Check your answer

Its knowledge stops where its training data stops, and it writes plausible text whether or not the text is true (learning record 0001). Today's fix for that gap is the same as for the manuals and the student records: put the missing fact in front of the model, at the moment it is needed. Context and memory are how that gets done on purpose rather than by luck.

Hold that thought. The model does not keep a running mind between calls. It sees the text in front of it, and nothing else. Whatever has to last longer than one moment must be written down somewhere else and brought back, and every design choice in this lesson is about where, when and how much.

The context window O3 5 min

A token is a small chunk of text, roughly a word or part of one; the next lesson covers tokens properly. The context is the set of tokens included when the model is called (Anthropic, Effective context engineering for AI agents), and the context window is the limit on how many tokens fit in one call. For the makerspace assistant, a single call carries several kinds of text:

  • the instructions: who the assistant is, what it may and may not do;
  • the tool descriptions, so the model knows what it can ask for;
  • the message history: the student's questions and the model's earlier replies;
  • the tool results: calendar rows, manual pages, whatever came back.

Anthropic's article describes context as a finite resource with diminishing returns (each extra token adds less than the one before), and gives the goal as finding "the smallest possible set of high-signal tokens" that gets the outcome you want (same article). That is a design principle you can quote at your review: every token has to earn its place.

Figure 1 shows why this matters inside a single request. A manual page returned by a tool is far longer than the student's question, so tool results quickly become the largest block. And the window is not only a hard limit. The same article describes context rot: as the number of tokens in the window grows, the model's ability to recall information from it decreases. So a fuller window costs more and works worse.

A common mix-up

"More in the context is always better, because then the model has everything." It is tempting because more information sounds safer. But the model has to find the one fact that matters among everything else, and the more text surrounds it, the more easily it is buried. Past a point, extra text makes the answer to a question like "is this student trained?" harder to find, and every token is still paid for. Try it below.

Kept between steps, and between sessions O3 5 min

Two different questions hide inside "does the assistant remember?" The first is about steps inside one request. The second is about visits days apart.

Between steps: the program resends

From your warm-up: every loop step is a separate model call, and the program runs the loop. The model holds nothing between calls. What carries a request forward is the message history: the program keeps a list of the question, each tool request and each tool result, and sends the whole list again on the next call. That is how step three "knows" what step one found. (This is the usual design of an agent loop, not a claim from the article cited below.) It also explains the shape of Figure 1: the list only grows, so each call is bigger, and costs more, than the last.

When the history nears the window limit, the usual fix is compaction: summarize the conversation and start a fresh window with the summary. Anthropic describes it as taking a conversation near the context limit and restarting with a summary, and advises tuning it by first maximizing recall, so the summary misses nothing important, and then trimming for precision (Anthropic). Clearing old tool results, which you did in the demo, is its lightest form.

Between sessions: nothing carries over by itself

A session is one conversation, from the student's first message until it ends. When the next one starts, the program builds a new, empty message history. The student's earlier chat is gone from the model's view, unless the program saved something and loads it back into the new window.

A common mix-up

"The assistant remembers me from last time." It feels true because chat products often seem to know you, and because a human assistant would. But the model is the same fixed program on every call, and a new session starts with an empty window. Whatever feels like memory was put there on purpose: a saved note, a stored profile, a summary the program loaded at the start. If your design does not save the training status and load it in session 2, the assistant will ask again, or worse, guess.

Read the figure in order: inside session 1 the long history is squeezed into a summary so work can continue; at the end one small fact is written to a file; in session 2 the history is empty and the only thing waiting in the window is the note the program loaded. Notice that the summary and the note do different jobs. The summary keeps one conversation going when it gets too long. The note outlives the conversation. Mixing them up is a design bug: if the training status exists only in a summary, it vanishes when the session ends.

There is also a cost angle you will meet properly next lesson. Because the program resends the history on every step, a long session pays for the same early messages again and again. Saving a short note and starting clean, instead of dragging a transcript along, is usually cheaper as well as more reliable. The next section covers two ways to design that logbook, and the shelf of manuals beside it.

Retrieval and notes as memory O3 5.5 min

The window is finite and gets worse when crowded. So the rest of what the assistant needs, the manuals and the student records, has to live outside it and be brought in when needed. There are two moves for that: retrieval and notes.

Retrieval: bring in only the relevant page

Retrieval means fetching a small piece of an outside source, such as one manual page, into the context when the question needs it. Anthropic's earlier article lists retrieval, tools and memory as the augmentations that turn a bare model into the building block of an agent, and notes that models can generate their own search queries and decide what to retain (Anthropic, Building effective agents). For you, retrieval is a tool: search_manual(machine, question) returns the best-matching page or two, and the model reads those instead of two hundred pages.

There are two timings. Up front means the program retrieves pages before the model is called, using a search over the manuals. Just in time means the agent holds lightweight pointers, such as a file path, a section title or a stored query, and loads the details itself when it decides it needs them. Anthropic describes this second pattern, and states its cost plainly: runtime exploration is slower than retrieving pre-computed data, and it needs thoughtful engineering so the model has the right tools and heuristics, or it can waste context chasing dead ends. It suggests a hybrid in some settings: some data up front for speed, and further exploration at the agent's discretion (Anthropic, Effective context engineering).

Notes: write it down, load it later

The same article describes structured note-taking, also called agentic memory: the agent regularly writes notes that are persisted outside the context window, and pulls them back in later (Anthropic). Its examples are a to-do list and a NOTES.md file. For the makerspace, the note is small and exact: jordan: 3D printer trained 2026-11-04; laser cutter not trained. At the start of a session the program loads that line. The note is the logbook.

Which timing should the makerspace assistant use? The manuals are long but stable, and students ask about them in narrow terms ("how do I clear a jam"), so the assistant can fetch a page when a question needs one, and a hybrid is natural: load the student's note and the short booking rules up front, and retrieve manual pages just in time. The price is a few extra steps on manual questions, each of which is another model call. That is a trade you can state at your review: fewer tokens per request, in exchange for a little more latency and the work of writing a good search tool description.

Compare the two on Figure 3. Retrieval is read-only: the manual does not change, and the agent just pulls the right page. Notes are read and write: the agent changes the file, so it is how new facts, like a student passing a training, survive to the next session. That difference decides which tool gets which job.

A common mix-up

"Retrieval gives the model a memory of the manuals." It does not: retrieval copies a page into this one call, and the next call has to fetch it again or keep it in the history. The model never learns the manual. This matters for budget, since pages you leave in the history keep costing space on every later step, which is why clearing them helps.

Worked example: a returning student O3 5 min

Now do what you will do in your design review: decide, item by item, where each piece of information goes. There are three choices, and each answers one question.

  • Keep in context: needed on this very call.
  • Save as a note: must survive to a later session.
  • Retrieve from the manual: large, stable, needed only sometimes.
Worked example

Jordan, who finished the 3D printer training two weeks ago, asks: "Can I book the 3D printer on Friday?" The candidate items are: (1) the assistant's instructions and tool descriptions, (2) Jordan's training status, (3) the calendar result for Friday, (4) the 200-page printer manual, (5) a transcript of Jordan's chat from last visit.

  1. Instructions and tool descriptions: keep in context. The model needs them on every call, so they belong in every window. They are fixed and short next to a manual, so keeping them is cheap.
  2. Training status: save as a note, load at session start. It has to survive between visits, and it is tiny. It then sits in the window, because the booking decision needs it right now. The question to ask is "does it outlive this session?", and it does.
  3. Calendar result: keep in context for now, clear later. It is needed for this answer only. Once Jordan's booking is made, the raw rows have done their job and can be cleared; a note is wrong for it because the calendar will change.
  4. The whole manual: leave outside, retrieve a page if asked. Booking does not need the manual at all. If Jordan next asks "what temperature for PETG?", the assistant calls the retrieval tool and loads one page.
  5. Last visit's transcript: do not carry over. It is long and mostly irrelevant. If something in it mattered, like a newly passed training, a note should have been written at the time. Loading the transcript would spend window space and add noise.

Notice the pattern behind the five decisions. Each came from asking two questions: does it have to outlive this session, and is it needed on this call?

Needed on this callNot needed on this call
Must outlive the sessionNote, loaded into the window (training status)Note, left in the file until a later session
Does not outlive itKeep in context (instructions, calendar rows); large and stable, retrieve a page insteadDrop (last visit's transcript)

Result: the window for this call holds instructions, the one-line note, and the calendar rows. That is a small, high-signal context, which is the target Anthropic describes.

Loading it spends token budget on every step of every request for text that is mostly irrelevant, and a fuller window means weaker recall of the facts that matter, which is context rot. A short note holds what outlives the session at a fraction of the cost.

Summary O3 2 min

  • The context is everything the model sees on one call: instructions, tool descriptions, history and tool results. It is finite, and a fuller window means weaker recall.
  • Between steps the program resends the history. Compaction and clearing old tool results keep it small.
  • Between sessions nothing carries over by itself; only what is saved and reloaded does.
  • Retrieval brings in one relevant page on demand. Notes are written by the agent and reloaded later. Like the engine, the logbook and the shop manual: what runs now, what is recorded, and what is looked up.
