Why the assistant must remember a student O3 2 min

Picture the assistant on a Tuesday. Maya asks how to change the focus lens on the laser cutter. The assistant needs the right page of a long manual. A week later Maya asks to book the laser cutter, and the assistant has to know she already passed the safety training, or it will wrongly send her to a class she finished. Two different problems are hiding in that story:

  • Too much to read: the manual is far longer than what you want to send to the model on every call.
  • Nothing carries over: a new visit starts from scratch unless something was saved.

Both come down to one question: what text does the model get to see when it answers? You already know from the language-model lesson that a model works only from its training plus the text it is given. This lesson is about managing that given text, which is what agent builders call context.

It is also where the money goes. Each step of the loop sends the model a request, and what that request contains determines how much it costs (Context windows). Choosing what goes into each request is most of the craft.

The map for this hour

First what the model sees on one call and why that pile grows (with a demo you run), then notes that survive between sessions, then finding one page in a long manual, then your own sort of the assistant’s data. By the end this sentence should feel natural: “it is in context, it is retrieved when needed, or it is saved between sessions, and here is why.”

A word on numbers. The token counts in this lesson are invented to make the arithmetic easy, and the lesson says so wherever it uses them. The facts that come from sources, like the 200,000-token guideline, carry a link.

Warm-up: the loop, one call per step O2 3 min

Before we look at what goes into each call, check that the loop itself is solid. This is the same recall practice as the quiz you already took, so try it from memory first.

Recall 1

Trace the request “Is the laser cutter free on Friday?” through the loop. Which tool gets called, what comes back, and who actually runs the tool?

Check your answer

The model is given the question and the tool list and replies with a request to call something like check_calendar for Friday. The program around the model runs that tool, takes the result (say, “free 1 pm to 4 pm”) and sends it back to the model in the next call. The model then writes the final answer. The model never runs anything itself, which matters today: whatever the program decides to put in the next call is all the model will see.

The loop above took two model calls. Is the second call a continuation of the first, as if the model were still “thinking”?

Check your answer

No. Each step is a separate call, and the model does not keep anything from the previous call by itself. The program has to send the earlier material again. That one fact explains most of this lesson.

Recall 3

A language model produces text one token at a time. From the first lesson, what two things does a model have to work from when it writes an answer, and which of them can your program change from one call to the next?

Check your answer

It has what it learned in training, and the text it is given in that call. Training is fixed once the model is built, so the only lever your program has is the given text. That lever is what we call context, and managing it is the whole of this lesson. It is also why a chatbot can state an outdated fact with confidence: nothing in its input told it the fact had changed.

If you got all three, you are ready. If the first one wobbled, the part of the loop worth rereading is “the program runs the tool, then calls the model again.” Everything below rests on that second call being a fresh, separate request that the program assembles.

A common mix-up

“The model runs the tool, and it remembers what happened.” Both halves are tempting because chat apps feel like one continuous thought. In the loop, the program runs the tool and builds each new request, including everything the model should still know. If the program leaves something out, the model has no way to recall it (Context windows).

The context window O3 9 min

The context window is “all the text a language model can reference when generating a response, including the response itself” (Context windows). Think of it as the model’s working memory for one call.

Models count that text in tokens, which are pieces of text, often whole short words and parts of longer ones. You do not need the exact rule. A useful rule of thumb comes from the retrieval post: 200,000 tokens is about 500 pages of material (Introducing Contextual Retrieval), so a printed page is a few hundred tokens. Tokens are also the unit you are billed in, which is why the window and your budget are the same conversation.

What counts toward the window

The documentation is blunt: “Everything in the request counts toward the context window: the system prompt, every message … (including tool results, images, and documents), and your tool definitions” (Context windows). The reply the model writes counts too. For your assistant that means four kinds of things share one limited space:

  • The system prompt: your standing instructions (“you help students at the makerspace”).
  • The tool definitions: the descriptions of check_calendar, book_slot and the rest.
  • The messages: the student’s request and the model’s own replies and tool requests.
  • The tool results: calendar rows, manual pages, booking confirmations.

Every call sends the whole history again

This is the part that surprises people. Each turn’s input is the previous conversation plus the new message, and the model’s output becomes part of the input for the next turn (Context windows). So the loop from your warm-up does not send each tool result once. It sends it again on every later call, the way a car with a growing roof load burns more fuel on every mile, not just the mile where you loaded it.

Figure 1 shows five calls of a booking request. The numbers are made-up examples, but the shape is real.

Add the five bars: 1,300 + 2,900 + 3,300 + 5,900 + 6,200 = 19,600 tokens sent, for a conversation whose final state holds only about 6,350. The window size is a ceiling on one call. Your bill follows the sum over calls, and that sum grows faster than the window does.

Prompt caching can make repeated tokens cheaper, but the documentation is explicit that cached prefixes still occupy the window: caching changes what you pay, not whether the tokens count (Context windows).

Worked example: counting one request

Let’s do the arithmetic the way you would for your budget. Say the system prompt and tool definitions together take 1,200 tokens, and the student’s request takes 100. These are the same example numbers the demo uses.

Worked example

The assistant makes five calls for “Book the laser cutter for Friday at 2 pm.” How many tokens does the program send in total?

  1. Call 1 sends only what exists: 1,200 + 100 = 1,300 tokens. Nothing else has happened yet.
  2. The model asks for the calendar. The assistant’s tool request (100 tokens) and the calendar result (1,500) join the history, which is now 1,300 + 1,600 = 2,900.
  3. Call 2 sends all 2,900, including the part it already saw. The training lookup then adds 100 + 300 = 400, so the history is 3,300.
  4. Call 3 sends 3,300. The manual search adds 100 + 2,500 = 2,600, so the history is 5,900.
  5. Call 4 sends 5,900. The booking adds 100 + 200 = 300, so the history is 6,200.
  6. Call 5 sends 6,200 and writes a 150-token reply.
  7. Total sent: 1,300 + 2,900 + 3,300 + 5,900 + 6,200 = 19,600 tokens, about three times the final history of 6,350.

The reason this matters for your budget: the last calls are the most expensive, because they carry everything. If you can remove or avoid the 2,500-token manual result before calls 4 and 5, you save 2,500 tokens on each of them. That is the arithmetic behind every trimming technique in the next section.

Show a solution

Call 1 sends 1,300 and the calendar step grows the history to 2,900. Call 2 sends 2,900, then the training lookup makes it 3,300. Call 3 sends 3,300, then the booking makes it 3,600. Call 4 sends 3,600. Total: 1,300 + 2,900 + 3,300 + 3,600 = 11,100 tokens, against 19,600 with the manual search. One big tool result, riding along on two later calls, accounted for most of the difference.

Where the tokens come from in your assistant

Four habits keep the window under control, and each one is a design decision you control rather than something the model does for you:

  • Keep tool definitions short. They are part of every request (Context windows), so a rambling description is paid for on every call. The next lesson covers writing them well.
  • Make tools return less. A calendar tool that returns one week of rows is cheaper than one that returns the whole semester.
  • Watch the output too. The reply counts toward the window and becomes input to the next turn (Context windows).
  • Measure before you tune. Log the tokens per call for ten real requests, then find the biggest slice. Guessing wastes effort on the small slices.

Find the biggest slice, usually a tool result, and shrink that first.

A bigger window does not mean better answers

A common mix-up

“If the window is huge, I can dump everything in and the model will use it.” It is tempting because more information sounds like more help. But “as token count grows, accuracy and recall degrade, a phenomenon known as context rot” (Context windows). The engineering write-up calls context a finite resource with diminishing returns, and says this emerges across all models (Effective context engineering). Fifty pages of unrelated manual in the window make the one right page harder to use, and you pay for all fifty on every call.

What the model cannot do with the window

Three limits follow from everything above, and each one will come up in design discussions:

  • It cannot see what is not in the request. A student’s earlier chat, last week’s booking and page 212 of the manual are all invisible unless the program put them in. If an answer is wrong, the first debugging question is always “what was actually in the request?”
  • It cannot keep anything between calls on its own. The model is the same model on every call, and it does not carry state forward by itself.
  • It cannot use everything it is given equally well. Recall degrades as the window fills (Effective context engineering), so less, chosen well, often beats more.

The practical habit: when the assistant gives a wrong or odd answer, print the full request it received before you blame the model. Often the right page was never in the request, or a stale result was.

What is kept between steps O3 8 min

Within one run, the default is simple: the program keeps the history whole and re-sends it, until the window nears its limit (Context windows). Every step stays visible to the model, which is why it can finish a booking that took five calls. Before you read about the fixes, run the demo and feel the problem.

What the program decides, step by step

You saw in the demo that the model never decides what stays. The program does. Here is the procedure the program follows on each turn of the loop, which is also the place where you will add trimming:

  1. Build the request: system prompt, tool definitions, then the stored history.
  2. Call the model and receive either a final answer or a tool request.
  3. If it is a tool request, run the tool in your program and append the request and the result to the history.
  4. Check the size. If the history is past your limit, trim before the next call: clear old results, or compact.
  5. Go to step 1, until the model answers or a stop limit is reached.

Step 4 is the new part compared with the loop you already know. It is a few lines of Python in your program, using lists and dicts you already handle: the history is just a list of messages, and trimming means returning a shorter list. The platform can do some of this for you, and the documentation describes both options (Context windows), but it helps to know the shape of what is being done.

Two ways to free space

Real windows are far bigger than the demo’s 8,000 tokens, but they still fill during long jobs, and cost grows long before they do. Two standard fixes, from lightest to heaviest:

  • Clear old tool results. The engineering write-up calls it “one of the safest lightest touch forms of compaction,” with the reasoning that once a tool was called deep in the history, the agent rarely needs the raw result again (Effective context engineering). It is what the demo’s button did.
  • Compaction. The model summarizes the conversation and a new window starts from that summary (Effective context engineering). The summary keeps decisions and open problems and drops redundant tool output, so it is lossy: it can forget a detail you later need.

The platform documentation lists both as built-in options: tool result clearing, and server-side compaction as its main strategy for long-running agent work (Context windows).

TechniqueWhat it doesRiskGood for
Clear old tool resultsDrops raw results already usedModel cannot reread them; re-run the toolCalendar rows, manual lookups
CompactionReplaces history with a summarySummary can lose a detail you later needLong conversations
Do nothingKeep full historyCost grows; recall can degradeShort requests

For the makerspace assistant, most requests are short: a question, a lookup, a booking. Do nothing is right for most of them, and clearing is the first tool to reach for when a request drags on. Compaction is for a long, branching conversation, which a student asking about three machines might produce. The write-up also advises tuning a compaction prompt first for recall, so nothing important is dropped, and only then for precision (Effective context engineering).

A common mix-up

“Cleared means lost for good.” Cleared means gone from this window. Because the program runs the tools, it can run check_calendar again if the model needs fresh rows. Calendar data goes stale in minutes anyway, so for your assistant, re-fetching beats hoarding.

Check yourself

A student asks the assistant to compare three machines, and each manual lookup returns a long result. Late in the run, the window is nearly full of old lookups. Which move frees the most space with the least risk?

Show the answer

Clear the old lookups. They are the largest slices (Figure 2), the model rarely needs the raw text again once it has noted the facts, and the program can fetch one again on demand. Restarting loses the work, and a bigger window only postpones the problem.

Between sessions: notes as memory O3 10 min

Now the other half of the story: Maya comes back next week. Everything above lived inside one run. A session here means one conversation or run of the assistant. When the next one starts, the program builds a fresh request, and unless something put last week’s facts into it, they are not there. The model is the same model, and nothing in it changed (the language-model lesson: its knowledge is its training plus the text it is given).

So anything that must survive a session has to be saved outside the window and put back in at the start. The documentation’s advice for long-running agents is exactly that: design your state artifacts so that context recovery is fast when a new session starts (Context windows). Think of the service logbook in a car’s glovebox. A mechanic who has never seen your car reads it in two minutes and knows the oil change history, because someone wrote it down.

Structured note-taking

The engineering write-up names this pattern structured note-taking: the agent regularly writes notes that are persisted to memory outside the context window, and those notes get pulled back into the window later (Effective context engineering). It mentions an agent that maintains a NOTES.md file, which is a plain text file. For your assistant, the notes could hold:

  • Which trainings each student has passed (laser cutter, 3D printer).
  • Bookings made, so the assistant does not double-book.
  • Preferences worth keeping, like “prefers afternoon slots.”

Notice who does the work. The program, not the model, loads the notes file at the start of a session and saves updates to it. Often the model decides what to write, by calling a “save note” tool, just as it decides to call book_slot. Saving a note is a tool call like any other, which fits what you already know about the loop.

Procedure: a notes file that works

  1. Decide what must outlive a session. Training status yes; the text of last week’s manual lookup no.
  2. Write it as short, labeled facts (one line per fact), so it loads cheaply and the model can find the right line.
  3. Load it at the start of every session, before the student’s first message.
  4. Update it when a fact changes, replacing the old line instead of piling on.
  5. Prune it. Every note you load is tokens you re-send on every call, so the notes have a budget too.

Keep notes small and organized, because the point is fast recovery at session start (Context windows). A 20,000-token diary defeats the purpose.

Worked example: one student across two visits

Worked example

Maya finishes laser cutter training on Tuesday and books a slot on Friday. A week later she returns. Trace what the program does, with a notes file of one line per fact.

  1. Session 1 starts. The program loads the notes file. It has no line for Maya, so the model treats her as untrained and says so.
  2. The trainer records a pass. The program (or the model, through a “save note” tool) adds one line: Maya: laser cutter training done, Tuesday. The notes file is on disk, outside the window.
  3. She books Friday. A second line goes in: Maya: booked laser cutter, Friday 2 pm. The session ends. The window is thrown away, and with it everything the model saw, including all the tool results.
  4. Session 2 starts a week later. The window is empty. The program loads the notes file first, so Maya’s two lines are now in the new window. Nothing else from last week is.
  5. She asks to book again. The model sees “training done” and skips the training question. It cannot see the old calendar results, so it calls check_calendar again, which is correct because last week’s rows are stale.

Two things to notice. The model never “remembered” Maya: the program put two lines of text in front of it. And the notes held only the facts that stay true (training done), not the facts that expire quickly (what was free last Friday).

A test for every candidate note

When your team argues about whether something belongs in the notes, ask three questions of it, in order. Each one removes a class of clutter, and together they keep the file small enough to load on every session:

  1. Will it still be true next week? Training passed, yes. “The laser cutter is free at 3 pm,” no.
  2. Would a future session act differently because of it? A passed training skips a question; a pleasantry changes nothing.
  3. Is it a fact or a record? A fact is one line. A record, like a full booking history, stays in the system that owns it and is fetched by a tool.

A fact that passes all three is a good note. Anything that fails the first question belongs, at most, in the window for the current run. Anything that fails the third belongs in a database behind a tool, as the booking history does in the worked example later in this lesson.

Where the notes live, and what can go wrong

For a design team, a plain file or a small database table is enough to start. The format matters less than the habits. Three failure modes to plan for:

  • Never written. The model learned something but nothing saved it. Fix: make saving a required step, for example the program writes the training result itself when the trainer confirms it.
  • Never loaded. The note exists but the new session did not read it. Fix: load before the first model call, every time.
  • Stale or bloated. Old lines contradict new ones, or the file grows until loading it is expensive. Fix: replace lines instead of appending, and prune.

There is also a privacy question for a university deployment: a notes file about named students is personal data. That decision belongs to your team and your school’s rules; this lesson only flags that the notes design is where it comes up.

“The assistant learns from past chats, so it will remember Maya on its own.” Chat products can feel that way, which is why it is tempting. But the model does not change when you talk to it, and an empty window knows nothing about last week. Only what was saved and loaded back carries over. Retrieval: finding the right manual page O3 10 min

Notes handle small facts about students. The manuals are a different problem: they are long, and any one question needs only a page or two. Retrieval means searching a larger store and adding only the relevant pieces to the prompt. You have already seen the result in the demo, where search_manual returned 2,500 tokens of chunks and not the whole manual.

How retrieval works

The standard recipe has three steps. The manual is split into chunks, “usually no more than a few hundred tokens.” Each chunk is turned into an embedding, a list of numbers that captures what the chunk is about, and stored. At question time, the chunks whose meaning is closest to the question are added to the prompt (Introducing Contextual Retrieval). That is “find the page that talks about this” without reading the whole manual every time.

Meaning is not enough: add keyword search

Embeddings are good at meaning but “can miss crucial exact matches.” The post’s example is a query for “Error code TS-999”: an embedding search may return general error-code pages and miss the one with that exact code, while BM25, a keyword-ranking method, is particularly effective for unique identifiers and technical terms (Introducing Contextual Retrieval). Your manuals are full of such identifiers: part numbers, error codes like “E-14,” settings like “PWM 20 kHz.” So run both searches and combine the results.

Retrieve wide, then rerank

The post’s pipeline retrieves the top 150 chunks, then a reranker, a second step that scores each candidate against the question and puts the best first, keeps the top 20 for the prompt. Its failure measure, the share of relevant chunks missed in the top 20, fell from 5.7% for a plain embedding search to 1.9% with contextual embeddings, BM25 and reranking together. It also found 20 chunks worked better than 10 or 5 (Introducing Contextual Retrieval). The idea behind the numbers is the point: cast a wide net cheaply, then spend the prompt budget only on the best catch.

The 150 and 20 are what that post used in its experiments, not rules. Your own numbers should come from testing on your manuals: a few hundred tokens per chunk times 20 chunks is a few thousand tokens per lookup, which is already real money if the model re-sends it on every call.

Worked example: one question through the pipeline

Worked example

A student asks: “What is the maximum cutting speed for 3 mm acrylic on the laser cutter?” Trace how the assistant finds the answer.

  1. Before the question: the manual has already been split into chunks of a few hundred tokens each and indexed, once, offline. The chunks are not re-made per question.
  2. The model asks for search_manual with the query “maximum cutting speed 3 mm acrylic.” The program runs the search.
  3. Two searches run. The embedding search finds chunks about cutting settings in general. The keyword search finds the chunk containing “acrylic” and “3 mm” literally, and the results are combined.
  4. The reranker picks the best from the long candidate list. Only the top few chunks go back as the tool result.
  5. The model reads those chunks and writes the answer, citing the page. If the chunks do not contain the answer, a good assistant says so and does not guess.

Notice where the cost lands. The retrieved chunks become a tool result, and like any tool result they ride along on every later call in that request. A lookup that returns 20 chunks of 400 tokens adds 8,000 tokens to every following call. Return fewer chunks for easy questions, and clear the lookup once the answer has been written down.

Part numbers and error codes are not the only time keyword search helps. Setting names, material names and units (“3 mm,” “PWM”) behave like identifiers, and embeddings often blur small differences between them. If your testing shows wrong pages for such questions, check the keyword side first.

How you will know retrieval works

Retrieval fails quietly: when it returns the wrong chunks, the model still writes a fluent answer from them. So test it before you trust it, with a short procedure you can run in an afternoon:

  1. Collect ten real questions students might ask, such as “how do I change the lens” and “what does E-14 mean.”
  2. For each, note the page that actually answers it, by reading the manual yourself.
  3. Run the search and look at the chunks returned, before the model sees them.
  4. Count the hits: how many questions had the right page among the returned chunks?
  5. Change one thing at a time (chunk size, adding keyword search, the number of chunks returned) and count again.

This mirrors the metric in the source, which measured how often relevant chunks were missed in the top 20 (Introducing Contextual Retrieval). Your version is smaller and cruder, but it gives you a number to put in front of your team, which beats an opinion. It also tells you where a wrong answer comes from: a missed page means a retrieval problem, while the right page plus a wrong answer means a prompt or model problem.

Chunking: the choice you will actually make

Of everything in the pipeline, chunking is the setting your team will tune most. The source says chunk size, boundaries and overlap all affect how well retrieval works, and recommends testing them for your own material (Introducing Contextual Retrieval). A way to think about it, with a car in mind: cut the shop manual into pages that are too small and the torque value ends up on one page and the bolt it applies to on another. Cut them too large and each lookup drags in a lot of text you did not need.

  • Too small: a chunk says “tighten to 25 Nm” and never says which part, so the model cannot use it.
  • Too large: a chunk holds a whole chapter, so each lookup costs thousands of tokens for one fact.
  • Boundaries: split at headings and steps, not mid-sentence, so each chunk reads as a unit.
For later: the source also describes a refinement in which a model writes a short note (usually 50 to 100 tokens) saying where each chunk comes from, added to the chunk before indexing. It targets the “which part?” problem above (Introducing Contextual Retrieval). You do not need it on day one.

Retrieval as a tool, loaded just in time

In an agent, retrieval is usually a tool such as search_manual. The engineering write-up calls the general pattern just-in-time retrieval: the agent keeps lightweight identifiers, such as file paths, stored queries or links, and loads the data into context at runtime using tools (Effective context engineering). It costs some speed compared with preloading, but it keeps the window clean. Your assistant can hold “laser-cutter-manual, section 4” as a reference and fetch the text only when a question needs it.

A common mix-up

“A serious assistant always needs retrieval.” Not always. The retrieval post says that if your knowledge base is smaller than about 200,000 tokens (about 500 pages), you can put all of it in the prompt with no retrieval, and prompt caching can make that faster and cheaper (Introducing Contextual Retrieval). Retrieval is a tool for when the material is too big or too costly to carry. You will weigh that in the worked example.

Worked example

Place the tool definitions, the laser cutter manual and the calendar results. Assume, for illustration only, a 40,000-token manual, a 5-call request, retrieval that brings in 5 chunks of about 400 tokens (2,000 tokens) at call 2, and 1,000 tokens of calendar rows.

  1. Tool definitions: needed on every call, small, fixed. Always in context. They are part of the request every time (Context windows), so keep their text lean.
  2. Laser cutter manual: big, needed for few questions. Compare options. Whole in the prompt: 40,000 tokens x 5 calls = 200,000 tokens sent. Retrieved: 2,000 tokens arrive after call 2 and are sent on calls 3, 4 and 5, so 3 x 2,000 = 6,000 tokens. Retrieval wins by a wide margin here.
  3. Calendar results: needed this run, stale soon, not worth saving. In context while needed, cleared afterwards, never in notes.
  4. Check the catch: if all your manuals together stay under about 200,000 tokens, the whole-prompt option is viable, and caching could cut its cost sharply (Introducing Contextual Retrieval). Even then, context rot says a lean prompt may answer better, so test both on real questions.

One more item is worth sorting before the costs, because it trips people up: the model’s own reasoning about a request. It lives in context for the run and is gone afterwards. Nothing about it needs saving, and what the model concluded that matters, such as a cleared training, reaches the notes only if your program or a save-note tool writes it there. Apply the same three questions and you will find that most of what happens in a run is meant to be thrown away, which is a feature: it is what keeps the next session’s window clean.

Now count what your choice costs. Using the same invented sizes, compare the two manual strategies over a day of traffic, because your sponsor’s budget is about the total, not one request.

The table’s numbers are assumptions, so do not quote them to your sponsor. What you can quote is the method: tokens per call, times the calls that carry it, times requests. The ratio between the rows, in this example about thirty to a hundred times, is what justifies building a search index. And note the last row’s caveat: a fix always has a cost, and the honest design review slide names it.

Prompt caching is the main reason the first row may be less extreme in practice. The retrieval post says it can cut latency by more than 2x and cost by up to 90% when the whole knowledge base is in the prompt (Introducing Contextual Retrieval). Even a 90% cut leaves the first row several times costlier than the second in this example, but it is a legitimate option for a small knowledge base, so ask your platform’s pricing page what caching costs before you rule it out.

How to defend the sort at your design review

A reviewer will not accept “it felt right.” Use one sentence per item, in this shape, and the reasoning will be on the page:

  • Item and place: “The laser cutter manual is retrieved on demand.”
  • Reason from size and use: “because it is large and only a few chunks matter to any question.”
  • Cost in tokens: “about 2,000 tokens per lookup, instead of 40,000 on every call.”
  • Known risk and mitigation: “retrieval can miss exact codes, so we combine embeddings with keyword search.”

A second example: a long conversation

Worked example

A student spends twenty minutes comparing the laser cutter, the CNC router and the 3D printer for a project, asking many follow-up questions, then asks you to book one. Where does each kind of information go during that conversation?

  1. Standing instructions and tool definitions stay in context for the whole conversation. They are small and needed on every call.
  2. Each manual lookup arrives as a tool result. After the model has summarized what it learned in its reply, the raw chunks are old, so clear them.
  3. The student’s stated goals (“a 30 cm acrylic sign, needs to be done by Friday”) are small and always relevant, so they stay in the messages. If compaction runs, the summary must keep them.
  4. Training status is read once, from the notes loaded at session start, and stays as one line.
  5. At the end, the booking is written to the booking system by a tool, and one line goes in the notes, so next week’s session knows.

Notice that no single technique does the job. Clearing handles the lookups, the system prompt stays put, compaction is a safety net if the chat gets very long, and the notes handle next week. A real design mixes them, and the skill you are building is knowing which one fits each item.

Check yourself

A teammate proposes saving every manual lookup result into the notes file, so the assistant “never has to search twice.” What is the strongest objection?

Show the answer

The first option. Whatever is in the notes is loaded at the start of each session and re-sent on every call, so notes are for small, lasting facts. Big reference material belongs behind a search tool.

Your turn

Place the remaining two items: the student’s training status and the booking history (every booking made by every student this semester). First step given: apply the three questions to the training status. It is tiny, needed on nearly every booking, and must outlive a session. Now do the booking history yourself: which place, and what would you put in the notes versus fetch with a tool? Write your answer before you open the solution.

Show a solution

Training status: saved between sessions, loaded into context at session start. It is one line per student, so re-sending it is cheap.

Booking history: it is big and mostly irrelevant to any one request, so it should not sit in context, and it should not be loaded wholesale from the notes either. The notes can hold only a short summary line per student (“2 upcoming bookings”), while the full history lives in the booking system and is fetched by a tool, such as the calendar check, when a question needs it. This is just-in-time retrieval for structured data: a reference, not the contents.

The first mistake to avoid is saving everything in the notes “just in case.” Every saved line is a line you may have to re-send on every call, so save facts, and fetch records.

  • The context window is the model’s working memory for one call: system prompt, tool definitions, messages and tool results, all counted in tokens.
  • Each call re-sends the whole history, so cost follows the sum over calls, and more tokens can mean worse recall (context rot).
  • Between steps you can clear old tool results or compact the history; between sessions, only saved notes carry over, and the model does not change.
  • Retrieval puts only relevant chunks into the prompt: embeddings for meaning, BM25 for exact identifiers, then rerank. Skip it if everything fits in about 200,000 tokens.
