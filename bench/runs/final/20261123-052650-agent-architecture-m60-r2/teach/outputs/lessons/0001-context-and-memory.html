Why the assistant needs a memory O3 3 min

Picture a mechanic at a lift. The car in the bay is what they are working on right now. The thick shop manual sits on a shelf, and they open it to one page when they need a torque spec. The service logbook in the glovebox tells them what was done on the last visit. Those are three different kinds of memory, and a good mechanic never confuses them: they do not read the whole manual before touching a bolt, and they do not rely on remembering last month's visit.

Your makerspace assistant has the same three problems:

  • What is in view right now: the student's question and what the tools have returned so far. This is the context, the car on the lift.
  • What is carried between visits: a student's training status, so the assistant does not ask again on Tuesday what it learned on Monday. This is the logbook.
  • What is looked up on demand: one page of a long machine manual. This is the shelf.

This lesson takes them in that order. First we look at what a model can actually see, because everything else is a way of working around its limits. Then we see what stays between the steps of one request, what survives between sessions, and how the assistant finds the right page. You will do a short demo in the middle, and finish by sorting a real request into the three kinds of memory.

Here is the plan for the hour, so you know where each piece lands:

Two habits will help. First, whenever a new idea appears, ask where the information physically sits: inside the window, in a file, or in a store you search. Second, whenever a cost appears, ask who pays it and how often. Most of the design arguments you will have at your review come down to those two questions, so it is worth making them automatic now.

The three-way split (in view, saved outside, looked up) is this lesson's framing of ideas from Anthropic's Effective context engineering for AI agents. The article is the main source throughout, together with the context windows documentation.

Warm-up: the loop you already know O3 3 min

Recall 1: the loop

Trace "Is the laser cutter free on Friday?" through the agent loop. What happens after the calendar tool runs, and what happens to its result?

Check your answer

The program runs the tool, then sends the result back to the model, which either asks for another action or writes the final answer. The key word for today is sends: the result has to go somewhere the model can read it. Where it goes, and for how long, is this whole lesson.

Recall 2: the floor

You explained why a chatbot can state an outdated fact with confidence. What are the only two things the model draws on when it writes a reply?

Check your answer

What it learned in training, and the text it is given in this request. Nothing else. So any memory an assistant has, whether of the last five minutes or of last week, has to arrive as text in the request.

Recall 3: who does what

In the agent loop, who actually runs the calendar tool: the model or your program? And is each step one model call or one long conversation?

Check your answer

Your program runs the tool; the model only writes a request for it, as text. Each step is a separate model call, which is exactly why memory is a design question: nothing links the calls except what your program chooses to send.

If any of those felt shaky, that is fine; the quiz on the agent loop is the place to check them. Today's lesson only needs one thing from them: each call starts from nothing except what the program hands over.

Recall 4: predict

Before the demo in section 4: in the agent loop, each step adds a message and a tool result. Do you expect the text the model reads per call to stay the same, grow a little, or grow every step? What would that do to cost?

Check your answer

It grows every step, because the program re-sends the earlier text along with the new. Cost per call therefore rises through a request, and the whole request costs the sum of all its calls. You will watch this happen in the demo and calculate it by hand.

A common mix-up

"The model remembers our earlier chats." It is tempting because chatbots feel like they do: you say your name once and it uses it later. But the model itself keeps nothing between calls. Each call is a fresh request, and the conversation seems continuous only because the program sends the earlier turns again each time. The documentation describes each turn's input as "all previous conversation history plus the current user message" (Context windows). If the program stops sending a message, the model has no trace of it. Keep this in mind: it is the reason every design choice below exists.

The context window O3 8 min

The context window is all the text a language model can reference when generating a response, including the response itself. The documentation calls it the model's "working memory", and says it is different from the large corpus the model was trained on: training is what the model learned in general, the window is what it can see for this one request (Context windows). Think of it as the dashboard and the bay: everything in view is usable, and everything not in view does not exist for the model.

What counts toward it

It is easy to assume the window holds just the chat. It holds more. The documentation lists the system prompt, every message (including tool results, images and documents), and your tool definitions, and the model's own output counts too (Context windows). For your assistant, that means:

  • The system prompt: the standing instructions ("you are the makerspace assistant; only book equipment a student is trained on").
  • The tool definitions: the description of the manual search, calendar and booking tools. They are sent every time, so a long, wordy definition is a cost you pay on every call.
  • The messages: the student's questions and the model's replies and tool requests so far.
  • The tool results: whatever each tool returned, such as a manual page or a list of free slots.

What a request actually looks like

Seeing the shape of a request in code makes "the window" less abstract. Below is a simplified sketch of what your program would hand the model for one student's question. It is illustrative, not the exact format of any particular library, but the pieces are the ones the documentation lists.

request = {
    "system": "You are the makerspace assistant. Only book machines "
              "the student is trained on.",            # system prompt
    "tools": [search_manual_def, check_calendar_def,
              book_slot_def],                           # tool definitions
    "messages": [
        {"role": "user",
         "content": "Can I book the laser cutter Friday?"},
        # later steps append here: the model's tool request,
        # then the tool result, then the next request...
    ],
}

Everything in that dictionary is text the model reads. Anything that is not in it, the model cannot use. Notice that you, the programmer, are in charge of what goes in. This is the whole lever you have: designing the assistant's memory means deciding what request contains on each call.

  • To make the assistant know something, put it in system or messages.
  • To make it forget something, stop sending it.
  • To make it remember across visits, store it yourself and put it back in next time.

Tokens: the unit of the limit and of the bill

A token is a chunk of text, the unit in which a model reads and writes (you met this in the first session: the model produces text one token at a time). The window's size is a limit counted in tokens, and every response reports how many tokens it used (Context windows). You will meet the same unit again when we cost the assistant, because usage is billed in tokens too. For now, remember one rule: more text in the window means more tokens, and more tokens means more room used and more money spent.

Window sizes vary by model. The documentation states that many current models have a 1M-token window, while others have 200k (Context windows). That is large, which is exactly why the next idea matters.

Figure 1 is the picture to hold. Like a fuel tank, the window has a fixed capacity. The first two segments are the fixed load you carry from the first call. The last two grow as the loop runs, and tool results usually grow fastest, because a manual page is far longer than the one-line request that fetched it.

A common mix-up

"If it fits in the window, the model will use it well." It is tempting to treat the window like a hard drive: if there is space, nothing is lost. The sources say otherwise. The documentation notes that "more context isn't automatically better" and that as the token count grows, "accuracy and recall degrade, a phenomenon known as context rot" (Context windows). The engineering article describes this as "a performance gradient rather than a hard cliff": the model does not fail at the limit, it gets gradually worse as the window fills, so context is "a finite resource with diminishing marginal returns" (Effective context engineering).

Why the window is not the whole answer

With a large window, a natural idea is to skip memory design: send everything and let the model sort it out. Three things argue against it, and each one will come back in your design review:

  • Cost. Tokens are counted per request, and the full request is sent again each call. A bigger window gives you room to be wasteful; it does not make waste cheaper.
  • Quality. Past a point, extra text makes recall worse, not better (context rot, above).
  • Persistence. No window size helps across sessions. A new session is a new window, however large.

The engineering article gives the underlying idea a name: the model has an "attention budget," and "every new token introduced depletes this budget by some amount" (Effective context engineering). Spending that budget on the right text, and not spending it on the rest, is what the field now calls context engineering: "curating and maintaining the optimal set of tokens" during a run. The rest of the lesson is context engineering applied to your assistant.

A related point from the same article: the system prompt should be specific enough to guide the model but not a brittle pile of if-else rules. "Minimal does not necessarily mean short"; start minimal and add instructions where you see failures. You will need this when you write your assistant's prompt.

What is kept between steps O3 9 min

Now the loop. Each call to the model is separate, so what it "remembers" from step to step is whatever the program sends again. The documentation describes the pattern: the input of each turn "contains all previous conversation history plus the current user message," and the model's output "becomes part of the input for the next turn" (Context windows). Tool results are no exception: the second call of a tool-using turn contains every block of the first, plus the tool result.

That has a consequence worth stating plainly. Nothing is dropped unless the program drops it, so the window only grows, and every later call re-sends everything before it. Step 8 of a request does not cost 1 unit of reading; it costs the sum of all eight steps' worth of text again. For the assistant, that means re-reading every manual page it has fetched so far before each new tool call.

The cost, worked by hand

Use the demo's own example numbers (in thousands of tokens) to see why this matters for your budget. The fixed load is 3k of system prompt plus 4k of tool definitions, and the student's question is 1k. Each step adds a 1k message plus a tool result.

Worked example

How much does the model read across the first three steps, if nothing is cleared? Results are 6k, 9k and 12k.

  1. Call 1 sends the fixed load and the question: 3 + 4 + 1 = 8k.
  2. Call 2 sends everything before it, plus step 1's 1k message and 6k result: 8 + 1 + 6 = 15k.
  3. Call 3 sends call 2's window plus step 2's 1k message and 9k result: 15 + 1 + 9 = 25k.
  4. Call 4 adds step 3's 1k and 12k: 25 + 1 + 12 = 38k.
  5. Added up, the four calls read 8 + 15 + 25 + 38 = 86k tokens, though the window only ever held 38k of distinct text. The sum grows faster than the window because early text is re-read on every call.
Your turn

The first step is given: call 1 reads 8k. Using the same numbers, what does call 5 send, if step 4 adds a 1k message and an 8k result and nothing was cleared? Then say how much smaller call 5 would be if you had cleared the first three tool results (6k, 9k and 12k) before it.

Show a solution

Call 5 sends 38 + 1 + 8 = 47k. Clearing the three old results frees 6 + 9 + 12 = 27k, so call 5 would send 47 − 27 = 20k, a bit over 40% of the uncleared size. The saving repeats on every later call, which is why clearing early beats clearing late.

One caveat on price: the documentation says prompt caching "changes what you pay for those tokens, not whether they count" toward the window (Context windows). Caching can make re-sent text cheaper, but it does not shrink the window or cure context rot. The arithmetic here counts window size, not price.

This is the pattern behind your sponsor's budget: cost per request is not "one question's worth of text" but the sum of every call's window. Long, tool-heavy requests are the expensive ones, and the cheapest fix is to stop re-sending text the model no longer needs.

The two fixes

  • Clear old tool results. Once a tool was called deep in the history, the raw result is rarely needed again. The engineering article calls this "one of the safest lightest touch forms of compaction" (Effective context engineering); the documentation lists "tool result clearing" among its context-editing options (Context windows). The cost: if the agent needs that page again, it must fetch it again.
  • Compaction. When the conversation nears the limit, it is summarized and a new window starts from the summary. The article says the summary keeps things like decisions and unresolved problems and discards redundant tool output (Effective context engineering). The cost: whatever the summary left out is gone.

A procedure you can reuse when you design the loop's housekeeping:

  1. List what each tool returns and how big it usually is. The biggest results are your clearing candidates.
  2. Decide which results the model needs only once (a manual page it has already answered from) and which it may need again (the student's booking request).
  3. Clear the first kind after the step that used it; keep the second kind.
  4. Set a threshold, such as "compact when the window passes 80% of the limit," so the decision is made by the program and not left to chance.
  5. Test with a long request, like the eight-step one in the demo, and check that the answer is still right after clearing.

Step 5 matters: clearing and compaction can both lose information the next step needs, so you check them on a long case, not a short one.

The documentation also notes that some models can track their remaining window and are told their token budget, and it describes server-side compaction as the primary strategy for long-running agent workflows (Context windows). You do not need these details today; they matter when you build the loop in code.
A common mix-up

"Windows are huge now, so keep everything." It is tempting because a 1M window feels endless, and deleting things feels risky. But you saw the two costs in the demo: every call re-sends everything, so the bill rises, and irrelevant old text dilutes the model's attention. The article says larger windows alone are unlikely to solve context pollution and relevance problems, and that the aim is "the smallest possible set of high-signal tokens" (Effective context engineering). Think of a glovebox: a bigger glovebox does not mean you should stuff in every receipt since the car was new.

What is kept between sessions: notes as memory O3 9 min

A session is one run of the assistant from its first message to when it ends, such as one student's visit. Everything so far lived inside one session's window. When the session ends and a new one starts, the window starts empty: the model has no trace of Monday's visit on Tuesday. The only things that can come back are things that were saved somewhere outside the window and then read in again. The documentation puts the design advice this way: "design your state artifacts so that context recovery is fast when a new session starts" (Context windows).

Notes: the logbook

The technique has a name: structured note-taking, where the agent regularly writes notes that are "persisted to memory outside of the context window" and pulls them back into the window later when needed (Effective context engineering). The article's examples are an agent that keeps a to-do list and an agent that maintains a NOTES.md file. If this workspace feels familiar, it should: a tutor like me starts every session with an empty window and rebuilds what it knows about you from your notes file and your learning records.

The article describes an agent playing a Pokémon game that kept tallies across thousands of game steps, such as a note that it had been training a character for the last 1,234 steps toward a target level (Effective context engineering). Without being prompted about memory, it built maps, tracked achievements and kept notes on how its fights went. Your assistant's version is much smaller, and that is good news: a student's training status is a handful of facts.

Three kinds of thing worth saving

Not everything an assistant could save is worth saving. A useful way to decide is to sort candidates by what the next session will do with them:

  • Facts about the person or the world that will still be true next time: training status, which machines they are cleared for, their preferred pickup time. These are the core of your logbook.
  • Commitments in flight: a booking made, a request waiting for a staff member's approval. The next session must know about these or it will contradict the last one.
  • Lessons about how to help: "this student asked for step-by-step instructions twice." Useful, but optional; add it only after the first two work, because every saved item is a token cost on every future visit.

Things not worth saving: the full chat, tool results you can fetch again (a manual page, the calendar), and anything that goes stale within the hour. The article's agents "kept notes" because the notes were cheaper than reconstructing the state, and that is the test: save a thing when reading the note is cheaper than rediscovering it.

Either way, start with the simplest option that works. You can move to a database when your questions outgrow a file.

What makes a good note

A note is useful if the next session can act on it in seconds. Use this checklist when you decide what to save:

  • Small: save the fact, not the conversation ("laser cutter: trained, 14 Oct"), not the full transcript.
  • Structured: a fixed shape, such as one record per student with one line per machine, so the assistant can find it without searching.
  • Written when it becomes true: save a booking right after it succeeds, not at the end of the session, which might never come.
  • Read when it matters: load a student's record at the start of their request, not everyone's records.
  • Owned by the program: the program decides when the file is written and read. The model proposes a note; the code stores it.

When a note is wrong

Suppose a staff member tells the assistant: "Maya's laser cutter training was revoked after the safety incident." The old note still says "trained." Three things must happen, in this order:

  1. Overwrite the note, do not append to it, so there is one current answer: save_note("maya", "laser_cutter", {"trained": False}).
  2. Record who and when in the note, so a later reader can see it was a staff decision and not a guess by the model.
  3. Check at the point of use: the booking step reads the note again right before booking, so a stale copy sitting in an old window cannot authorize a booking.

The third step is the important one. A note copied into the window is a snapshot; the file is the truth. Anything that must be correct at the moment of an action should be read at that moment, by code.

A note store in code

Your first version does not need anything fancy. A JSON file per student, read at the start of a session and written when something changes, is already a memory system. This sketch is illustrative; you have the Python skills to write it now.

import json, pathlib

def load_notes(student_id):
    path = pathlib.Path("notes") / f"{student_id}.json"
    return json.loads(path.read_text()) if path.exists() else {}

def save_note(student_id, key, value):
    notes = load_notes(student_id)
    notes[key] = value
    path = pathlib.Path("notes") / f"{student_id}.json"
    path.parent.mkdir(exist_ok=True)
    path.write_text(json.dumps(notes))

# notes = {"laser_cutter": {"trained": "2026-10-14", "expires": "2027-03-01"},
#          "last_booking": "laser cutter, Fri 14:00"}

The loop then does two things around the model. At the start of a request it calls load_notes and puts the result into the window (in system or the first message). When a tool succeeds, such as a booking, it calls save_note. The model never touches the file directly; it asks, and your code acts, exactly as in the agent loop.

Notice how little goes into the window: one student's record, a few lines, not the whole database. That is the same discipline as retrieval, applied to notes.

A common mix-up

"Compaction is memory between sessions." It is tempting because both involve a summary. But compaction works inside one long session: it shrinks the window so the session can continue. Notes are written outside the window on purpose, so that a brand-new session with an empty window can read them. The article lists compaction and note-taking as separate techniques with different best uses: compaction for long back-and-forth, note-taking for work with clear milestones (Effective context engineering). Compaction shortens one long session; notes are the logbook that outlives it.

Retrieval: finding the right page O3 9 min

The third memory is the manual, which may run to hundreds of pages across many machines. Pasting it all into the window fails twice over: it may not fit, and even if it does, you pay for it on every call and the model attends to it less well (the context rot above). The answer is retrieval: bringing into the window only the text that is relevant to the question at hand, from a store that sits outside it.

The engineering article describes two timings for this, and a mix of the two (Effective context engineering):

  • Up-front retrieval: relevant text is surfaced before the model answers, often using embedding-based search, and placed in the window. The program does the looking.
  • Just-in-time retrieval: the agent keeps only lightweight identifiers, such as file paths, stored queries or links, and loads the data with tools when it needs it, inside the loop. The model does the looking.
  • Hybrid: some data up front for speed, and the agent explores further on its own. The article's example is Claude Code, which drops CLAUDE.md files into context up front and uses glob and grep to fetch files just in time.

Read Figure 2 against the agent loop you already know. The bottom lane is the loop: the search tool is simply one more tool, and its result is one more tool result entering the window, subject to everything from the last two sections. The top lane is not a loop at all: the program searches once, in code, before the model is called.

How a search finds the page

You will hear two words here. Keyword search matches the words in the question to words in the page, like a book's index. Embedding-based search, which the article mentions for up-front retrieval, matches by meaning, so "how do I make the cut deeper" can find a page about power settings that never uses the word "deeper." The article does not say which to prefer, and for a few dozen manuals either can work; start with whichever your team can build and test first.

Whichever you pick, the loop is the same:

  1. Take the question (or the model's search query).
  2. Search the store and return the few best-matching sections.
  3. Put those sections into the window.
  4. Let the model answer from them, and tell it to say so when the answer is not in the text it was given.

The last step guards against a failure you already know from the first session: a model asked a question it cannot answer from its window will still produce plausible text. Retrieval gives it something true to draw on, but it does not make it check; your prompt has to.

Worked example: splitting a manual

The laser cutter manual is one long document. How do you prepare it so a search can return one section?

  1. Split at the manual's own headings, such as "Focus and power" and "Cleaning the lens", because a heading already marks one self-contained topic.
  2. Give each piece an identifier and a title: laser-cutter/focus-and-power. Titles are what search results show first.
  3. Check the sizes. If one section is 8k tokens, split it further; if one is 100 tokens, merge it with its neighbor so it carries enough context to be useful.
  4. Test with five real questions from students, and check that the right section comes back near the top for each.

What a good retrieval looks like

However you search, the result is a tool result that enters the window, so the same rules apply. The article stresses that tools should return token-efficient information, and that if a human engineer cannot say which tool should be used in a situation, an agent cannot be expected to do better (Effective context engineering). For your manual search that suggests a procedure:

  1. Split each manual into labelled pages or sections, so a result can be one section and not a whole file.
  2. Make the search tool return a few short matches with titles first, and let the model ask for one section in full. The article describes this as letting each step inform the next (Effective context engineering): titles first, then one section.
  3. Keep identifiers the model can reuse, such as "laser-cutter / focus-and-power", so it can refetch a section later instead of holding it.
  4. Describe the tool plainly and separately from the other tools; overlapping tools make the choice ambiguous.
  5. Clear old search results once answered, using the housekeeping from section 4.

The trade-off

Up-frontJust-in-time
SpeedFast: data is pre-computedSlower: the agent explores at runtime
RiskWrong or stale pages loaded before the model decides what it needsThe agent can misuse tools or chase dead ends without good guidance
NeedsAn index built ahead of timeGood tools and descriptions

The article states the speed and risk points directly: "runtime exploration is slower than retrieving pre-computed data," and without guidance an agent "can waste context by misusing tools, chasing dead-ends," and it suggests the hybrid may suit less dynamic content, adding that "do the simplest thing that works" will likely stay best advice (Effective context engineering). For a manual that rarely changes, that points toward a simple design.

Retrieval and the budget, with numbers

Here is the same argument in tokens, using invented but plausible sizes. Suppose the laser cutter manual is 30k tokens and a typical answer needs one 2k section. Suppose a request takes four model calls.

  • Paste the whole manual: 30k of manual is in the window on every call, so the request reads about 4 × 30k = 120k tokens of manual alone.
  • Retrieve the section: a 2k section enters once and stays for the remaining calls, so about 4 × 2k = 8k tokens of manual, and less if you clear it after answering.

That is roughly a fifteenfold difference, from one design choice, before counting the other machines' manuals. Your sponsor's budget is the reason to prefer retrieval; the quality argument (less to dilute the model's attention) is a second reason that points the same way. Both numbers are examples: measure your real manuals and the real token counts your calls report (the documentation notes that every response reports its token usage), and then argue from your own figures.

A common mix-up

"Just paste the whole manual into the prompt." It is tempting because it needs no search code and the window is big. But it fills the window with text for every machine when the student asked about one, you pay for all of it on every call, and the surplus competes for the model's attention (Context windows). Retrieve the page for the laser cutter, not the manual for the whole shop.

Check yourself

A student asks, "What material settings do I use on the vinyl cutter?" You search the manuals before the model is called and load the top page. What kind of retrieval is this?

Show the answer

The first option. The program searched before the model call and filled the window, so it is up-front retrieval.

Worked example: the makerspace assistant O3 9 min

Now put the three memories together on one real request. For each piece of information, ask three questions in order: does the model need it in view right now? Must it outlive the session? Is it too big to carry and only partly needed?

Worked example

A student writes: "Can I book the laser cutter Friday?" Sort what the assistant needs.

  1. The student's question and the booking result go in context. They are needed now, and they are small. After the session they are not needed in full, so only the outcome is worth saving.
  2. The student's training status is a note. It must survive between visits, it is a few lines, and it is read at the start of the request (arrow 1 in Figure 3). If it lived only in the window, the assistant would forget it every time.
  3. The laser cutter manual is retrieved. It is long and only one page matters for this question, so the assistant fetches that page (arrow 2) and lets old pages be cleared once the answer is given.
  4. The booking is saved as a note after it succeeds (arrow 3), so tomorrow's session knows it happened. The calendar is a tool, so the booking itself lives in the calendar, not in the model.

Notice what the figure shows and what it does not. The model sees only the middle lane, and the program moves information between the lanes with its arrows. That is the central design fact of this lesson: the model has no memory; the program builds one out of notes and retrieval, and spends the window on what the current step needs.

Your turn: sort three more

The first is done for you. Sort each item into context, note or retrieved, and give a reason in a few words.

  • Done: the 3D printer manual's section on bed leveling → retrieved: long, and only one section matters for this question.
  • That a student's laser cutter training lapses on 1 March.
  • The list of free slots the calendar tool just returned for Friday.
  • The CNC router's full safety manual, when a student asks which end mill to use.
Show a solution

Lapse date: a note. It must survive between visits and is a single fact, so the assistant can read it at the start of any request (and compare it to today's date in code).

Free slots: context. It is needed this step to answer or book, and it goes stale quickly, so it does not belong in a note. Once the booking is done it can be cleared.

CNC safety manual: retrieved. Fetch the page on end mills, not the whole manual; a long manual in the window costs tokens on every call and dilutes the answer.

The third option. Static content suits pre-computed retrieval, which is fast and simple, and you can add a search tool later if students' questions turn out to need exploration.

Spot the flaw

A teammate proposes: "At the start of every session, load all students' notes and every manual into the window, so the assistant always knows everything." What is the main flaw?

Show the answer

The third option. Load only this student's record and only the manual sections the question needs. Privacy is a real concern too, and loading one student's record at a time helps with it, but the memory-design flaw is the wasted window.

Worked example 2: a returning student

It is Tuesday. A student who passed laser-cutter training on Monday writes: "Book me the laser cutter Friday afternoon, and remind me how to set the focus." Trace what the program does.

  1. New session, empty window. The program loads the student's note (trained, with a date) and puts it in the first message. Without it, the model cannot know Monday happened.
  2. Two jobs in one question. The booking needs the calendar tool; the focus reminder needs the manual. The model requests both as tool calls, and your program runs them.
  3. The manual is retrieved, not loaded. The search returns section titles; the model asks for the focus section only. That one section enters the window.
  4. The result is used, then cleared. After the answer, the focus section is no longer needed; the booking confirmation stays in the messages.
  5. One note is saved. The program writes the new booking as a note. Tomorrow's session can read it; the focus section is not saved, because it can be looked up again.

Each item landed in the cheapest place that still works: facts that must survive in notes, bulky reference text in retrieval, working text in context.

Defending it at the review

A reviewer will push on your design. Here are the questions you should expect, each with the move that answers it:

  • "Why not just use a bigger model window?" Because no window carries over to a new session, and the section 4 argument about cost and recall applies at any size.
  • "What if the notes are wrong?" Store dates, let code check expiry, and let a staff member correct a record. A wrong note is trusted like a right one.
  • "What if retrieval returns the wrong page?" Return titles first, let the model ask for a section, tell it to say so when the text does not contain the answer, and test with real student questions.
  • "What does a request cost?" Sum the windows of all its calls, as in the hand calculation in section 4, then show what clearing saves.

If you can answer those four with numbers from your own prototype, you have a design that holds up. If one answer is "I do not know yet," that is your next experiment.

Three questions to carry to your design review:

  • Where does this piece of information live: in the window now, in notes, or in the manual store, and why there?
  • How many tokens does each call send, and what could be cleared before the next one?
  • If a session ended right now, what would the next one need to start well, and is it saved?
