Context and memory: what an agent sees, keeps and looks up

The program sends the result back to the model as part of its next input and calls the model again, so the model can decide its next step or write the final answer. Today's question is: what exactly is in that next input, and what happens to it afterwards?

What the model sees: the context window O3 5 min

A language model knows two things: what it learned in training, and the text it is given right now. Everything else you might call "knowing" has to arrive as text in that input. Anthropic defines context as "the set of tokens included when sampling from a large-language model" (Anthropic, Effective context engineering). The context window is all the text the model can reference when generating a response, including the response itself, and the Claude documentation compares it to the model's "working memory" (Claude docs, Context windows).

A token is the small piece of text the model reads and writes, often a short word or part of a word. The window is measured in tokens, and so is the bill: more tokens sent means more cost. That is why this topic is a budget topic for your team.

Think of the window as the workbench in a shop. Whatever is on the bench, the mechanic can use; whatever is in the cabinet across the garage does not exist for the next bolt unless someone carries it over. The bench is also finite, and a cluttered one slows you down.

What goes on the bench? The documentation lists it: everything in the request counts toward the window, namely the system prompt, every message (including tool results, images and documents) and your tool definitions (Claude docs, Context windows). For your assistant that is four kinds of thing:

  • Instructions: the system prompt ("you help students at the makerspace...") and the tool descriptions you will write.
  • The conversation: the student's messages and the assistant's replies.
  • Tool requests and results: every call the model made and everything that came back, such as calendar entries or manual pages.
  • Room for the answer: the model's reply also counts.
Check yourself

The booking database holds next month's laser cutter schedule, but no tool has read it yet. Can the model use that schedule when it writes its next reply?

Show the answer

No. The model sees only its context. A tool call is how data outside the window gets onto the bench.

Between steps: the context grows O3 5 min

Now the surprising part. The model does not remember step 1 when it is working on step 3. Each model call is a fresh read of the input, and per the documentation each turn's input is "all previous conversation history plus the current user message", while the model's output "becomes part of the input for the next turn" (Claude docs, Context windows). The memory within a session is your program: it keeps a list of messages and sends the whole list each time.

If you have written Python with a list of dicts, you already know the shape. The program appends the student's message, calls the model, appends the model's reply, appends the tool result, calls the model again. The list only grows, and every call pays to send all of it.

In your earlier trace there were three model calls for one question. Here is what each is sent:

CallInput holdsOutput is
1instructions, tool definitions, the questiona request for check_calendar
2everything in call 1, plus its request, plus the calendar resulta request for search_manual
3everything in call 2, plus its request, plus the manual textthe final answer

Think of an odometer rather than a fuel gauge: it never counts down, and each leg of the trip adds to the total. The first call is small, the last is the largest, and the whole request costs the sum of all three inputs, not the size of the final one.

A common mix-up

"By step 3 the model remembers steps 1 and 2 on its own." It feels true because the answer at step 3 clearly uses the calendar result. But it can use it only because the program sent it again. If your program leaves the calendar result out of the history, the model has no trace that it ever asked.

One practical consequence: a big tool result is expensive twice over. It takes space in the window, and it is re-sent on every later call. If a tool returns a 3,000-token chapter where 600 tokens of the right paragraphs would do, every remaining step pays for the difference. Failure is also possible: if the input alone is too long, the API rejects it with a "prompt is too long" error (Claude docs, Context windows).

More context is not better O3 4 min

If every call re-reads everything, why not make the window as big as possible and load all the manuals once? Two reasons: cost, which you just watched, and quality. Anthropic's engineers describe context rot: as the number of tokens grows, the model's ability to accurately recall information from the context decreases. They describe it as a "performance gradient rather than a hard cliff", and say models have an "attention budget" that every new token draws down (Anthropic, Effective context engineering). The Claude documentation agrees that "more context isn't automatically better" (Claude docs, Context windows).

The guiding rule from that post: find the smallest set of high-signal tokens that makes the desired outcome most likely. Picture a mechanic with the whole toolbox emptied over the bench. Everything is technically within reach, and finding the 10 mm socket takes longer.

A common mix-up

"Windows keep getting bigger, so I can stop worrying about what goes in." It is tempting because a bigger window means fewer "prompt too long" errors. But the same post says larger windows will not remove the problem of focus, and every extra token is sent, and paid for, on every later call. A bigger window raises the ceiling; it does not make clutter free.

Anthropic names three ways to keep a long task inside the window: compaction (summarize the history and restart a new window with the summary), structured note-taking, and sub-agents, which do focused work in a clean window and return only a short summary (Anthropic, Effective context engineering). Compaction and notes are in this lesson; sub-agents belong to the multi-agent lesson later.

Between sessions: notes as memory O3 5 min

Within a session the program keeps the message list. When the session ends, that list is gone unless the program saved it. The model itself keeps nothing between calls, let alone between visits. Chat apps feel like they remember because the app stores and reloads conversations for you; for your assistant, nobody does that unless you build it.

A common mix-up

"The assistant automatically remembers earlier conversations with each student." It is tempting because consumer chatbots seem to. In your own system, a new session starts with an empty window, as the demo showed when you pressed "Student comes back".

The fix is notes: the agent writes important facts to storage outside the window, and a later session reads them back in. Anthropic calls this structured note-taking: the agent "regularly writes notes persisted to memory outside of the context window", for example a to-do list or a NOTES.md file, and pulls them back in later (Anthropic, Effective context engineering). This workspace works the same way: your tutor reads NOTES.md at the start of each session, because it does not remember your last one.

Claude's API has a ready-made version, the memory tool. It is file-based and client-side: Claude asks for file operations under a /memories directory (commands include view, create, str_replace, insert, delete and rename), and your application runs them against your own storage. It also says to restrict every path to /memories so a request cannot reach other files (Claude docs, Memory tool). That is the same split you learned in the loop: the model asks, the program acts.

For your assistant, the design could be one small file per student:

/memories/student-4471.md
- laser cutter training: done 2026-10-02
- 3D printer training: not done
- prefers morning bookings

The documentation's multisession pattern is the same idea for long projects: an early session writes a progress log, later sessions read it first, and update it before ending (Claude docs, Memory tool). Decide what to save as carefully as what to load: a note is only useful if it is small, true and findable.

Training status is a fact someone could get wrong in a note. A booking system or training roster is a better source of truth than a note the model wrote. Notes suit soft facts, such as preferences and progress; look up hard facts with a tool.
Check yourself

Retrieval: finding the right page O3 5 min

Notes are memory you write. Retrieval is memory you look things up in: the manuals. A laser cutter manual may run to hundreds of pages, and you saw why loading it all each step is costly. Retrieval picks out a few relevant passages and puts only those in the context.

The standard recipe, called retrieval-augmented generation (RAG), has three preparation steps and a lookup. Anthropic describes it this way: split the corpus into chunks, usually no more than a few hundred tokens; use an embedding model to turn each chunk into a vector that encodes its meaning; store the vectors in a database that supports similarity search. At question time the query is matched against the chunks and the best ones are added to the prompt (Anthropic, Introducing Contextual Retrieval).

Two things to know when you design this. First, similarity search finds passages with a similar meaning, which can miss an exact label. Anthropic's example is a support database queried for "Error code TS-999": an embedding model may return general error-code content and miss the exact match, whereas BM25, a ranking function based on exact word matches, finds it. It is especially useful for unique identifiers and technical terms (Anthropic, Introducing Contextual Retrieval). Machine manuals are full of part numbers, error codes and setting names, so a hybrid of both searches fits your case.

Second, retrieval is not always needed. If your knowledge base is smaller than 200,000 tokens, about 500 pages, Anthropic says you can include all of it in the prompt with no retrieval, and prompt caching makes that faster and cheaper (Anthropic, Introducing Contextual Retrieval). Count your manuals before building a search system. And when you do retrieve, there is a choice about when: loading chunks before the model runs, or giving the model a search tool so it fetches pieces at runtime. Anthropic suggests a hybrid and adds that its best advice is "do the simplest thing that works" (Anthropic, Effective context engineering).

A common mix-up

"The model searches the manual itself, and semantic search always finds the exact page." The model never touches the manual: your program runs the search and pastes the result. And meaning-based search can miss an exact code like TS-999, which is why exact-match search is worth adding.

Check yourself

A student asks about "error E-417" on the CNC router. Which search is most likely to find the exact page that lists E-417?

Worked example and practice O3 4 min

Worked example: what does one request cost?

A request makes three model calls. The system prompt and tool definitions total 1,000 tokens, the question is 50, each tool request is 50, the calendar result is 2,000 and the manual result is 500. The final answer is output, so ignore it. How many input tokens are sent in total?

  1. Call 1 is sent the instructions and the question: 1,000 + 50 = 1,050.
  2. Call 2 is sent all of that, plus the first request and the calendar result: 1,050 + 50 + 2,000 = 3,100.
  3. Call 3 is sent all of call 2's input, plus the second request and the manual result: 3,100 + 50 + 500 = 3,650.
  4. Add the three inputs, because each call is billed for all it is sent: 1,050 + 3,100 + 3,650 = 7,800 tokens.
Your turn

Same setup, but now the calendar result is 500 tokens and the manual result is 2,000 (the big result comes later). Step 1 is given: call 1 is sent 1,050. Work out calls 2 and 3 and the total. Then say, in one sentence, why the total is lower than 7,800 even though the two results add up to the same 2,500.

Show a solution

Call 2: 1,050 + 50 + 500 = 1,600. Call 3: 1,600 + 50 + 2,000 = 3,650. Total: 1,050 + 1,600 + 3,650 = 6,300. It is lower because the 2,000-token result arrives last and is re-sent only once, in call 3, whereas an early big result is re-sent on every later call.

Write three lines for your assistant: what always sits in the context, what is saved between sessions, and what is looked up. Check them against the table of contents above.

Show an example

Always in context: system prompt, tool descriptions, the current conversation. Saved between sessions: each student's preferences and progress notes, loaded at the start of a visit. Looked up: manual passages by search, and calendar entries and training status by tool, not by memory.

Summary O3 2 min

  • The context window is everything the model sees on one call, measured in tokens: instructions, history, tool results and its own output.
  • Between steps the model keeps nothing; the program resends the whole history, so the context, and the bill, grow with every step.
  • More context is not better: it costs more on every call and can hurt recall, so keep the smallest useful set.
  • Between sessions nothing survives unless the program saves it: notes in files, read back at the start of the next session.
  • Retrieval puts a few relevant chunks in the window; combine exact-match and meaning-based search, and skip retrieval if everything fits.
