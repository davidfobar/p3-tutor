Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what it keeps in its context window, what it saves between sessions, and how it finds the right page in a long manual.

Why this matters for you

Your assistant has to answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three are context-and-memory decisions, and they are the ones your design review will ask you to defend.

Check your answer

Four: three calls that each end in a tool request, and a fourth that writes the answer. Remember that number, because each of those four calls is a fresh start for the model, and the next section shows why that matters.

Between steps: the model remembers nothing O3 8 min

Here is the big picture before any detail. An agent feels like one continuous mind working through your request, but that feeling is built by the program around the model. The model itself starts every call blank. What makes call 3 "know" what happened in call 1 is that the program wrote it down and sends it again.

Think of a mechanic who loses all short-term memory every time you hand them a part. To keep a repair going, you keep a clipboard: the job ticket, every step done so far, every measurement taken. Before each step you hand over the whole clipboard, they read it top to bottom, write one new line and give it back. The mechanic is not the memory. The clipboard is.

That clipboard has a name. The context window is all the text a language model can reference when it generates a response, including the response itself. The Claude documentation calls it a "working memory" for the model, and distinguishes it from the large body of text the model was trained on (Claude docs, Context windows, "How the context window works"). Training taught the model patterns, as in your first record. The context window is what it can see right now.

The same page spells out the mechanism: each user message and assistant response accumulates in the window, previous turns are preserved completely, and each turn's input is all the previous history plus the new message (Context windows). Your program does this resending. When the model asks for a tool, the program runs it and appends the result to the history before calling again.

A common mix-up (M9)

"The model keeps track of the conversation as it goes." It is tempting because a chat window looks like a continuous exchange. But the model has no internal storage between calls. If your program forgot to include the calendar result in call 3, the model would not know a calendar check ever happened. This is also why it matters, from the earlier lesson, that the program (not the model) runs each tool: the program owns the clipboard.

The context window and what it costs O3 9 min

A model reads and writes in tokens, pieces of text a bit smaller than a word on average (a word you have already heard; here is what it limits). The context window is measured in tokens, and it has a maximum size. What counts against it is more than the chat messages. The documentation lists everything in the request: the system prompt, every message including tool results, images and documents, and your tool definitions, with the model's own output counted as well (Context windows).

For your assistant that means the window holds, on every call:

  • The system prompt: its role, rules and tone.
  • The tool definitions: the name, description and parameters of check_calendar, search_manuals and the rest. This is how the model knows what tools exist, as in quiz 0001's last item.
  • The message history: the student's questions, the model's tool requests and its answers.
  • The tool results: a calendar listing, a manual page, a training record.

Think of the window as a car's dashboard: whatever is on it at this moment is what the driver can act on, and there is only so much room. Anything not on the dashboard is, for the driver at that moment, not there.

Why it affects cost

Because the whole history is sent as input on every call, a step's cost is not just the new text. It is the new text plus everything before it. The documentation describes each turn as an input phase of all previous history plus the new message, then an output phase (Context windows). Billing follows tokens, so a long result that enters the history on call 3 gets paid for again on call 4, and call 5, and so on until the session ends.

The car version: a tool result is like a heavy box left in the trunk. It costs fuel on every trip until you take it out. Your sponsor's budget is the fuel budget.

Prompt caching can make repeated text cheaper to process, but the documentation is explicit that it changes cost, not capacity: cached prompt prefixes still occupy the context window (Context windows). You will not need caching for the design review; just know it exists.

A trace with numbers

Here is the laser-cutter request from your agent-loop record with invented but easy token counts, the same ones the demo uses. The system prompt is 500 tokens and the tool definitions are 700, so every call starts with 1,200 tokens before the student has said a word. The question is 60. Each tool request is 40 and the calendar result is 200. If the manual tool returns a 600-token page, the table below is what the program sends.

CallWhat the model has just been givenInput tokens
1fixed 1,200 + question 601,260
2call 1's input + request 40 + calendar result 2001,500
3call 2's input + request 40 + manual page 6002,140

Three things to notice. First, the fixed 1,200 tokens are paid on every call, so a short system prompt and tight tool descriptions save money on every single step. Second, the total input is 1,260 + 1,500 + 2,140 = 4,900 tokens, which is more than the 2,140 in the last call, because the early text is sent repeatedly. Third, swap the 600-token page for a 6,000-token manual and call 3 alone becomes 7,540 tokens. You will see the same arithmetic in the demo. A small model budget makes this arithmetic a design input, not a detail.

Also notice that the output counts: the model's own words are part of the history the next call receives, which is why long, chatty answers have a delayed cost as well as an immediate one. Output tokens are billed too, and the documentation reports usage for the input and output of every request in a usage field, so you can measure this in your own program once you call the model from code (Context windows).

What happens when it fills up

If the input alone is too large for the window, the API returns a 400 error, "prompt is too long". On newer models, a response can also be cut off with the stop reason model_context_window_exceeded when generation hits the limit (Context windows, "Context window overflow behavior"). Either way, a loop that never trims its history will eventually fail. That is a second reason, besides the step limit from the loop lesson, for a long-running agent to have a plan for its context.

A fuller window is not a better one O3 9 min

If cost were the only problem, you could shrug and pay. The second problem is quality. In the demo you saw that the whole manual took up most of the window. You might think a model with a large window should simply be given everything, so nothing is missed. The evidence says otherwise.

A common mix-up (M7)

"A bigger window, filled with everything we have, gives the best answers." It is tempting because more information sounds safer. But the documentation says more context is not automatically better: as token count grows, accuracy and recall degrade, a phenomenon called context rot (Context windows). Anthropic's engineering team describes it the same way, based on needle-in-a-haystack tests: as tokens increase, the model's ability to recall information from that context decreases, and every model shows it, some more gently than others (Effective context engineering for AI agents).

The same article gives a reason and a goal. The model has a finite "attention budget": every new token draws it down, because the model relates every token to every other. So the goal is "the smallest possible set of high-signal tokens" that makes the right result likely (Effective context engineering). The documentation draws the conclusion: curating what is in context matters as much as how much room there is.

An engine analogy: stuffing more fuel into a cylinder does not give more power. The mix has to be right. Your job is to choose the mix.

Four ways to keep the window lean

These are the tools the sources describe. You do not need to build them now; you need to know which problem each one solves.

  • Return less from tools. The cheapest fix is at the source: have search_manuals return one relevant page, not the manual. The next sections show how to find that page.
  • Clear old tool results. Once the model has used a result, the program can drop it from the history. The documentation lists tool result clearing as part of context editing, "clear old tool results in agentic workflows" (Context windows, "Manage context with compaction").
  • Compaction. When a long session nears the limit, summarize it and restart with the summary. In Claude Code the summary keeps architectural decisions, unresolved bugs and implementation details, and drops redundant tool output (Effective context engineering, "Compaction"). The documentation calls compaction the primary strategy for long-running agent workflows.
  • Sub-agents with clean windows. A helper agent works in its own fresh context, possibly using tens of thousands of tokens, and returns only a short summary, often 1,000 to 2,000 tokens (Effective context engineering). We return to when this pays off in a later lesson.

For your assistant, a typical student session is short: a few questions, a calendar check, a booking. It will probably never need compaction. The takeaway for a short session is the first item: do not let one tool dump a manual into every later call.

Between sessions: notes as memory O3 10 min

Everything so far lives inside one session. Now the other boundary. When a student closes the chat and returns on Thursday, the window is empty. Nothing from Tuesday is in it, because nothing carries over by itself. You saw that in the demo's session 2.

A common mix-up (M3)

"The assistant remembers earlier conversations, like a person would." It is tempting because a good assistant seems to know you. But a model call sees only its input, and a new session builds a new input. Memory across sessions exists only if the program stores something and puts it back in the window. Quiz 0001 had this as a trap: automatic memory of earlier conversations is not what makes a system an agent.

The way to give an agent memory is plain and a little humbling: it writes notes to a place outside the window, and reads them at the start of the next session. Anthropic's context-engineering article calls this structured note-taking, or agentic memory: the agent regularly writes notes persisted outside the context window and pulls them back later. Its examples are a to-do list and a NOTES.md file (Effective context engineering, "Structured note-taking"). Your learning workspace works this way. The tutor reads NOTES.md and your learning records at the start of every session, because it has no other way to know you.

The article's showpiece is Claude playing Pokémon. The agent kept tallies across thousands of game steps, such as how many steps it had trained in one area and how far a level target was, kept maps of explored regions and notes on which attacks worked. After context resets it read its own notes and continued sequences that ran for hours (Effective context engineering). Nothing in the model changed. The notes did the remembering.

How the memory tool works

You do not have to invent the mechanics. Claude's memory tool is documented as a way to store and retrieve information across conversations through a directory of files. It is client-side: the model asks for an operation, your program carries it out against storage you control, and your program returns the result, just like any tool in the loop (Memory tool docs). That is the loop you already know. The six commands are view, create, str_replace, insert, delete and rename, and paths begin with /memories, which your code maps to real storage, such as one folder per student or rows in a database (Memory tool docs, "Tool commands").

The typical flow for the makerspace assistant would go like this:

  • A session starts. The first thing the model does is view /memories; the docs say Claude checks its memory directory before starting a task.
  • It reads the student's file, for example /memories/students/jamie.md: "Laser cutter training done Oct 3. Prefers afternoon slots."
  • During the session, it writes updates as it goes, since, in the docs' words, "your context window might be reset at any moment".
  • The window is discarded at the end; the file remains.

The documentation also lists responsibilities that fall on you, not on the model. A path such as /memories/../../secrets.env could reach outside the memory folder, so your handler must validate every path. Claude usually refuses to write sensitive information, but for a stronger guarantee you strip it in your handler. And you cap file sizes and expire old files (Memory tool docs, "Security considerations"). For a university makerspace this matters: a student's training status is fine to store, while anything personal should be kept out.

What belongs in notes, and what does not

A note is only as good as what the assistant chose to write, and a stale or wrong note is worse than none, because it goes back into the window looking like fact. A simple rule for the makerspace: if another system already holds the fact exactly, look it up there; if the fact is something the assistant learned in conversation, and a future session would want it, write it down briefly.

Retrieval: finding the right page O3 12 min

Notes are short and written by the agent. The machine manuals are long and written by someone else. You cannot paste them into every call (the window section showed the cost, the rot section the quality), and you cannot expect the assistant to have memorized them. So the assistant needs a way to find the right few pages when a question comes in. That is retrieval: look up relevant information in a knowledge base and add it to the prompt (Anthropic, Contextual Retrieval). In the shop manual analogy, the dashboard shows only what you need; the manual stays on the shelf until you look something up.

First, do you need it at all?

Retrieval adds machinery, so check whether you can skip it. Anthropic's guidance: if your knowledge base is smaller than 200,000 tokens, about 500 pages, you can include the entire knowledge base in the prompt, and prompt caching makes that cheaper and faster (Contextual Retrieval, "A note on simply using a longer prompt"). Be careful reading this. It says it is possible, not that it is best for you. The rot section told you that every extra token has a quality cost and a per-call cost, and your budget is small. For a handful of short manuals it may be reasonable. For a shelf of long ones, retrieval is the route.

The usual recipe

The common approach, as described in that article, is to prepare once and search every time:

  1. Chunk: break each manual into pieces, usually no more than a few hundred tokens each.
  2. Embed: run each chunk through an embedding model, which turns text into a list of numbers that encodes its meaning.
  3. Store: keep these in a vector database that can search by similarity of meaning.
  4. Search: when a question arrives, embed it the same way, find the most similar chunks and add them to the prompt.

(Contextual Retrieval.) In the agent loop, that search is simply a tool: the model calls search_manuals("how to focus the laser cutter") and the program runs the search step above and returns a few chunks as the tool result. Retrieval is a tool call whose result is chosen to be small and relevant. This is the connection to everything else in today's lesson.

Where retrieval goes wrong

A common mix-up (M8)

"Search by meaning always finds the right page." It is tempting because embeddings sound like understanding. But embeddings, the article says, excel at semantic relationships and can miss crucial exact matches. Their example: for the query "Error code TS-999", an embedding model may return general error-code content and miss the exact "TS-999". A keyword method called BM25, a lexical ranking function, finds precise words and phrases and does well on unique identifiers and technical terms (Contextual Retrieval). A makerspace manual is full of identifiers: model numbers, part codes, error codes like a printer's E-47. Combine both methods and merge their ranked lists.

A second failure: a chunk can lose its context. The article's example is a chunk that reads "The company's revenue grew by 3% over the previous quarter." Nothing in it says which company or which quarter, so a search for a specific company's results cannot match it. The fix, contextual retrieval, is to prepend a short, chunk-specific explanation, usually 50 to 100 tokens generated by a model, before indexing. In a manual, the equivalent is a chunk saying "Hold the trigger for two seconds" with no hint that it belongs to the 3D printer, not the laser. Prefixing each chunk with "From the Laser Cutter manual, section: Focusing" fixes that.

The reported effect, measured as how often the right chunks are missing from the top 20 results: 5.7% for standard embeddings, 3.7% with contextual embeddings, 2.9% with contextual embeddings plus contextual BM25, and 1.9% when a reranking step is also added (Contextual Retrieval). Treat these as one lab's measurements on its own data sets, not a promise for your manuals. The point to carry into a design review is the direction: exact matching plus context makes a measurable difference.

Up front, or just in time?

One more design choice, from the context-engineering article. Many systems run retrieval before the model starts, loading chunks into the prompt. A just-in-time approach keeps lightweight pointers, such as file paths or links, and lets the agent load what it needs with tools while it works. Just-in-time is more flexible but slower, and needs good tool descriptions, or the agent wastes context. A hybrid retrieves some data up front for speed and lets the agent explore further. Claude Code, for example, drops its CLAUDE.md files into context at the start and uses search tools for the rest (Effective context engineering). For your assistant, the natural hybrid is: put the short, always-needed rules in the system prompt, and let the model call search_manuals only when a question needs a manual.

Worked example and practice O3 7 min

Now apply all of it to one request, in the order you would in a design review: what is in the window, what survives the session, and how the manual is found.

Worked example

Alex messages the assistant: "Book me the 3D printer Saturday at 2, and what nozzle size do I use for PETG?" Alex has never used the assistant before, and has finished printer training, which is recorded in the makerspace's system.

  1. List what the window holds at call 1. System prompt, tool definitions (calendar, booking, manual search, training record) and Alex's message. Nothing else, because nothing carries over (M9, M3).
  2. Choose what tools return. check_training_record returns a short yes or no with a date. search_manuals returns the top two chunks, each prefixed with its machine and section, not the manual. Each small result is resent on later calls, so small results are cheap results (the cost section).
  3. Decide what is saved. The training status is in the official record, so it is looked up, not trusted from a note. What is worth a note is something the assistant learns that the record does not hold, such as Alex's preference for Saturday afternoons. One line in /memories/students/alex.md.
  4. Decide how the manual is found. The question mentions a material (PETG) and a setting (nozzle size), mostly plain language, so semantic search suits. Part numbers and error codes need keyword search too (M8), so use both.
  5. Check the end of the session. The window is discarded. The note remains. Next week the first call is view /memories/students/alex.md, and the preference is available again.

A checklist for your design review O3 3 min

Here is the lesson turned into a procedure you can run on your own sketch of the assistant, and defend one line at a time.

  • Window: write down everything that is in the window at the last call of your longest realistic request, with a token guess for each piece. Which piece is largest? If it is a tool result, can the tool return less?
  • Cost: multiply your fixed pieces by the number of calls in a typical request, and add the repeated tool results. Compare this with your sponsor's budget per request.
  • Between steps: check that your program, not the model, appends each result to the history. Confirm nothing is expected to be "remembered" any other way.
  • Between sessions: list each fact the assistant needs on a return visit and say whether it is looked up in a system of record or written as a note. For each note, say who can read it and when it expires.
  • Manuals: state the total size of your manuals in tokens. If it is small, justify why you do or do not skip retrieval. If you retrieve, say how exact codes are found and how a chunk keeps its machine name.
  • Limits: decide what happens when a session grows long: clear tool results, summarize, or stop and start fresh with notes.

None of these answers is fixed; the review panel will want the reason behind each one, and the reasons are what this lesson gave you.

Summary O3 2 min

  • The model keeps nothing between calls. The program resends the whole history, so the context window, which holds the system prompt, tool definitions, messages and tool results, is the agent's working memory, and every token in it is paid for again on each call.
  • A fuller window is not a better one: context rot. Keep tool results small, clear or compact old history, and give sub-agents their own windows when a task is big.
  • Nothing survives between sessions unless the program stores it. Notes written to files outside the window, read at the start of the next session, are the memory; an official record is the source for facts that must be exact.
  • For long manuals, retrieval puts only the best chunks in the window. Use keyword search alongside semantic search for exact codes, and give chunks their context.
