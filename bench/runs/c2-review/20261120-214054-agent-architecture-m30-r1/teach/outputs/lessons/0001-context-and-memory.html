Context and memory: what the assistant sees, keeps and looks up

By the end of this lesson you can say, for the makerspace assistant, what stays in the context window, what gets saved between visits, and how it finds the right page of a long manual.

Objective O3: context and memory in an agent About 30 min reading + 6 min demo = 36 min Builds on the agent loop
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status from one visit to the next. Both jobs come down to one question: what text does the model get on each call? Your design review will ask you to defend that answer, and your model budget depends on it.

Warm-up O2 2 min

Three questions from earlier sessions, because everything today rests on them. Answer in your head first, then check.

Recall

The model decides it needs check_calendar. Who actually runs that tool, and where does its result go next?

Check your answer

The program around the model runs it. The model only writes a request that names the tool and its arguments. The program then sends the result back to the model as part of its next input. That second half is today's topic: "part of its next input" is the context.

Recall

Where does a model get its knowledge, apart from training?

Check your answer

Only from the text it is given in the current call. So if the assistant is going to know a manual page or a student's training status, someone has to put that text in front of the model. Context and memory are the ways to do that.

Recall

The model asks for check_calendar, and the program runs it. After that, is the model called again, or is the loop over? Why?

Check your answer

It is called again. The result has to reach the model as new input before it can decide the next step or write the final answer, so every step is a separate call. Today's lesson is about exactly what each of those calls contains.

The context window: everything the model is sent O3 5 min

Here is the big picture before the details. A car driver has a dashboard and the road in view: that is all they can use to decide what to do right now. Anything else, like the service history or the shop manual, has to be fetched. A model is the same. Its context window is all the text it can reference when it writes a reply, including the reply itself. The docs call it the model's "working memory", and they separate it from the large body of text the model was trained on (Claude Docs: Context windows). This is the same fact you showed in your earlier session on what a model does (learning record 0001), that a model knows only its training plus the text it is given. The window is that text.

Text is measured in tokens: chunks of text, often a word or a piece of a word. The window has a fixed size in tokens, and everything has to fit in it. Models differ in size; some windows hold around 200,000 tokens and some a million (Context windows), so never design around one remembered number.

What counts toward the window? More than the student's question. The docs say everything in the request counts: the system prompt, every message including tool results, and the tool definitions, plus the output the model writes (Context windows). Two of those need a word: the system prompt is the standing instructions the program always sends first, such as the assistant's role and rules, and the tool descriptions are the names, purposes and parameters of the tools, which is how the model knows what it can ask for. Anthropic's engineering team describes context as the set of tokens given to the model, and the job of curating that set as the real design work (Effective context engineering for AI agents).

You already wrote this in Python terms when you read JSON. Picture the context as a list of dicts:

context = [
    {"role": "system",    "content": "You are the makerspace assistant. Rules: ..."},
    {"role": "tools",     "content": "check_calendar(machine, date), read_page(manual, page), ..."},
    {"role": "user",      "content": "Is the laser cutter free Friday?"},
    {"role": "assistant", "content": "CALL check_calendar(laser cutter, Friday)"},
    {"role": "tool",      "content": "Free 2 to 4 pm"},
]

This is a simplified sketch, not any provider's exact format. The point is the shape: one growing list, and the model is sent all of it each time.

Now trace your own example from the agent loop, "Is the laser cutter free on Friday?", and write down what the model is sent on each call:

  • Call 1. System prompt, tool descriptions, the question. The model replies with a request: check_calendar(laser cutter, Friday).
  • The program runs the tool and gets "Free 2 to 4 pm".
  • Call 2. Everything from call 1, plus the model's request, plus the result. The model replies with the final answer.
  • The program shows the answer to the student and appends it to the history, ready for the next question.

Two calls, and the second contained the first in full. Nothing about call 1 was stored inside the model; call 2 simply included the earlier text. Keep that in mind, because it explains both the cost and the memory limits that follow.

    What is kept between steps and between sessions O3 4 min

    The demo made two things visible. First, within one session, the model call at step 3 had no secret copy of step 2. The program sent the whole stack again, with the tool result added. Every step is its own call: the model is called once per input it receives, and the tool runs are done by the program. The docs describe the window as holding the conversation history plus the new output the model generates (Context windows). So "kept between steps" means "still in the list the program sends".

    Second, between sessions the list is gone. When you started next week's session with notes off, the window held a system prompt, tools and the manual, and nothing about Sam. The memory tool's docs are blunt about it: your context window might be reset at any moment, so anything not written to a memory file can be lost (Claude Docs: Memory tool).

    A common mix-up

    "The assistant remembers me; chatbots do." In a chat product, somebody has built that memory. A bare model call has none: it sees only what is in its input. The docs for the memory tool say it plainly: "Memory lives entirely in your application" (Memory tool). If your team wants the assistant to know Sam's training status on Thursday, your team writes the code that saves it and loads it back.

    Think of a car. The dashboard shows speed and fuel right now: that is the window. The service logbook in the glovebox is still there after you turn the engine off: that is saved memory. The dashboard does not recall last week's oil change unless somebody wrote it in the book.

    A common mix-up

    "By step 3 the model remembers step 2." It is tempting because a chat feels continuous. But the model only has what the program put in the call. If the program forgot to append the tool result, the model at step 3 would never have seen it, however carefully it had read it a moment earlier.

    Why the window cannot just be bigger O3 4 min

    Reasonable instinct after the demo: "Fine, use a model with a huge window, paste in all the manuals, and skip the cleverness." Two things push back.

    Cost. The demo's counter "Sent to the model so far" kept growing faster than the window itself, because each call re-sends everything. More tokens in each call means more for the model to process on every step. This is the lesson's own reasoning from how the loop works, and it is why cost per request, one of your constraints, is mostly a question about what you put in the window. The docs list everything that counts toward the window (Context windows). Check your provider's pricing page for the actual rates; this lesson uses none.

    Quality. Anthropic's engineers describe context rot: as the number of tokens in the window grows, the model's ability to recall information from it goes down. They call context a finite "attention budget" with diminishing returns, so the goal is the smallest possible set of high-signal tokens that gets the job done. The decline is a gradient, not a hard cliff (Effective context engineering). The docs make the same warning about accuracy and recall (Context windows).

    A common mix-up

    "If the whole manual fits, put the whole manual in." It is tempting because it needs no extra code. In the demo, the whole-manual mode used 950 of the 1,000 tokens before the student had said anything, and every later call paid for that again.

    When a long task does outgrow the window, there are options. Compaction summarizes a conversation that is near the limit and starts a new window with the summary, keeping things like decisions and unresolved bugs and dropping redundant tool output. The lightest form is clearing old raw tool results, since a raw result deep in the history is rarely needed again (Effective context engineering). The next two sections cover the other two tools: retrieval and notes.

    Retrieval: finding the right page O3 4 min

    Retrieval means fetching the right piece of a large store and putting only that into the window. Anthropic describes two timings (Effective context engineering):

    • Up front. Many apps use embedding-based retrieval, a search by meaning that runs before the model does and drops the results in; a later lesson can cover it.
    • Just in time. The agent holds lightweight identifiers, such as file paths, stored queries and links, and uses tools to load the data when it needs it.

    The demo's index mode was just in time. The window held the page titles (an index), and when the student asked about the blade, the model requested read_page(band saw, blade change). The program ran it and added one page to the window. The model did not search anything: it asked, and the program fetched, exactly like check_calendar.

    Walk through one call. The student asks about the blade. The model sees the index line "p. 3: blade change" in its window and writes the request read_page(band saw, 3). The program looks up page 3 in its files, appends the text as a tool result, and calls the model again. Now the window holds the question, the request, the page and the index, but not pages 1, 2, 4 or 5.

    Claude Code mixes the two timings: some files are placed in the context up front, and others are found at runtime. The article also notes the trade-off: exploring at runtime is slower than having data ready, and without good tools an agent can waste context chasing dead ends. Its advice is to do the simplest thing that works (Effective context engineering).

    For your assistant, a suggested first design (this is the lesson's advice, not the article's), as a procedure:

    • Keep a short index of each manual's sections in the window or behind a tool.
    • Describe read_page clearly so the model can tell when to use it.
    • Have it return one page (or section), not the manual.
    • If the index cannot find the right page, then consider search over the text; that is a later step, not the first one.
    A common mix-up

    "Retrieval means the model searches the manuals itself." Like every tool, retrieval is run by the program. The model's contribution is choosing what to ask for, from the tool descriptions it was given. Weak descriptions mean wrong pages, which is why the article tells you to check whether a human engineer could say which tool to use in a situation (Effective context engineering).

    Notes as memory O3 4 min

    Retrieval answers "how do I find the right page". Notes answer "how do I remember Sam". The idea, which Anthropic calls structured note-taking, is that the agent writes notes to something outside the context window and reads them back in later (Effective context engineering). Their examples are a to-do list and a NOTES.md file.

    One example they give is Claude playing Pokémon. It tracked progress over thousands of game steps with notes like "for the last 1,234 steps I've been training my Pokémon in Route 1, Pikachu has gained 8 levels toward the target of 10". After its context was reset it read its own notes and carried on (Effective context engineering). The window restarted, and the notes were still there.

    You saw it in the demo with the notes box ticked. One step, the model asked the program to save a line. Then, next week, the program loaded that line into the fresh window, and the assistant could say Sam was trained.

    How it works on one real platform, as an illustration: Anthropic's memory tool gives the model file commands on a /memories directory, among them:

    • view: look at what is stored; the model checks its memory before starting a task.
    • create: write a new file, such as a note about Sam.
    • delete: remove one.

    The model only requests those operations. Your application executes each one against storage you control and returns the result. The docs list project context across sessions, lessons from past interactions and a growing knowledge base as uses (Claude Docs: Memory tool). You can build the same pattern yourself with a folder of text files and two tools.

    A common mix-up

    "Memory means the model learned something." Nothing about the model changed. A file changed, in storage your program controls, and next time the program put its text back into the window. Because it is just a file, you can read it, correct it and delete it, which matters when a student's record is wrong.

    Which technique when? Anthropic matches each technique to a kind of task (Effective context engineering):

    • Compaction: long back-and-forth conversations.
    • Note-taking: iterative work with clear milestones.
    • Sub-agents: complex research that benefits from parallel exploration. They get their own lesson later.

    For a makerspace assistant, notes are the natural fit for training status, because it is a small fact that must outlive a session. That is this lesson's own judgment, not the article's.

    Worked example and practice O3 5 min

    Worked example

    Sort three items for the assistant: today's chat with Sam, Sam's laser cutter training status and the laser cutter manual (say 300 pages).

    1. Ask of each: how long does it need to live, and how big is it? Today's chat lives for this session and is small, so it belongs in the window and nowhere else.
    2. Training status must outlive the session and is a tiny fact, so it goes in the notes file, and the program loads it at the start of each session (a few tokens).
    3. The manual is large, mostly irrelevant to any one question and does not change per student, so it is looked up on demand: an index plus read_page.

    Result:

    ItemWhereWhy
    Today's chatWindowNeeded now, small, ends with the session
    Training statusNotes file, loaded at startMust survive between visits, tiny
    ManualLooked up on demandLarge, only one page matters at a time
    Worked example: what does one request cost in tokens?

    Use made-up round numbers, as in the demo: system prompt 500, tool descriptions 800, a manual index 300, the student's question 50, a tool request 40, a calendar result 100, one manual page 700, the final answer 200. Compare two designs for the question "Is the laser cutter free Friday, and how do I change the lens?"

    1. List the model calls. With an index there are three: a calendar request, a page request, and the final answer. (The calendar and page lookups could happen in either order.)
    2. Size what call 1 is sent: 500 + 800 + 300 + 50 = 1,650. Its reply adds 40.
    3. Call 2 is sent call 1's input, the 40-token request and the 100-token result: 1,650 + 40 + 100 = 1,790. Its reply (the page request) adds 40.
    4. Call 3 adds that request and the 700-token page: 1,790 + 40 + 700 = 2,530. The sum of what was sent is 1,650 + 1,790 + 2,530 = 5,970.
    5. Now swap the index for a 60,000-token manual in the window. That design needs only two calls, because there is no page to fetch. Call 1 is sent 1,650 − 300 + 60,000 = 61,350; call 2 adds the 40-token request and 100-token result: 61,490. The sum is 122,840. Same answer, about 20 times the tokens, even with one call fewer.

    These are illustrative numbers, not a price quote. The pattern is the point: you pay for the window on every call, so a large item that is always in it is paid for again at every step.

    Procedure: where does an item go?
    • How long must it live? One session means the window; longer means a saved file.
    • How big is it? Large means look it up, one piece at a time.
    • How often does it change? Often means fetch it live with a tool, not a saved copy.

    Summary O3 2 min

    • The context window is everything the model is sent on one call: system prompt, tool descriptions, history, tool results, plus its own output. It is working memory and it has a fixed size.
    • Between steps, only what the program re-sends is kept. Between sessions, nothing is kept unless the program saves it and loads it back.
    • A bigger window costs more on every call and recall gets worse as it fills, so put in the smallest set of high-signal text.
    • Retrieval fetches one page when it is needed, by a tool the program runs. Notes are files the program saves and reloads. Neither changes the model.

    A checklist for your design review. For each piece of information the assistant uses, you should be able to answer:

    • Is it in the window on every call, saved between sessions, or looked up on demand?
    • What does it cost in tokens, and how many times is that paid per request?
    • What code of ours saves it, loads it or fetches it? The model does not.
    • What goes wrong if it is stale, missing or wrong?

    Say it in your own words: Sam comes back next week. Explain, without looking, what the model is sent on the first call, and where each piece of it came from.
