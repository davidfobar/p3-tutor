What the assistant must remember O3 1.5 min

Picture a student, Sam, who finishes laser-cutter training on Monday. On Wednesday Sam opens the makerspace assistant and asks, "Can I book the laser cutter Friday, and what power do I use for 3 mm acrylic?" To answer well, the assistant needs three different kinds of information:

  • The working text for this request: the question, the calendar result, the instructions it was given. This is its context.
  • Something from Monday: Sam is already trained. This has to survive between visits, so it is memory.
  • One page from a manual hundreds of pages long: the acrylic settings. This is retrieval.

You will learn how each works and what each costs, then decide where each piece of information lives. Start with a prediction.

Predict first

Where do you think the assistant keeps Sam's training status between Monday and Wednesday?

Check your prediction

In a file or database that the program saves and loads again at the start of the next session. The model itself keeps nothing between sessions. Section 5 shows how.

A model knows only what it learned in training plus the text it is given. Training stops at some point, so newer facts are missing unless someone puts them into the text. That second half, "the text it is given", is the context window.

The context window: everything the model sees in one call O3 5 min

A model reads and writes text in small pieces called tokens. The context window is all the text the model can reference when it generates a response, including the response itself. Anthropic's documentation calls it the model's "working memory", and distinguishes it from the large body of text the model was trained on (Context windows). It is measured in tokens and it is finite: many current models allow up to 1M tokens and others 200k, depending on the model (Context windows).

Think of the bench next to a car on a lift. You can only work with the tools and parts laid out on the bench; whatever is in the garage cabinet is out of reach until someone brings it over. The window is the bench.

The key point is how much lands on the bench. Everything in the request counts: the system prompt, the tool definitions, every message including tool results, any images or documents, and the output the model generates (Context windows). Figure 1 shows it for one call.

A common mix-up: "the context is what the student typed"

In a chat app the visible text is your message and the reply, so it is tempting to think that is all the model sees. It is not. In Figure 1 the student's question is a sliver of the stack; the system prompt, the tool definitions and every tool result sit in the same window and are counted the same way (Context windows).

The second point is the one that shapes your design. You might reason that a window of 1M tokens means you can drop in everything and lose nothing. It does not work that way: as the token count grows, accuracy and recall degrade, an effect called context rot (Context windows). Anthropic's engineers add that the decline is gradual rather than a cliff (Effective context engineering for AI agents). Their stated aim is "the smallest possible set of high-signal tokens" that makes the outcome you want likely.

There is also a cost. Whatever you send again is part of the request's input, and the documentation says tokens kept from earlier turns, such as kept thinking blocks, are billed as input tokens like the rest of the conversation history (Context windows). A bigger window is a bigger bench, and you pay for what you put on it each time.

Between steps: the program resends everything O3 5 min

Now put the context in motion. In the agent loop, every step is a separate model call. The model keeps nothing from the last call: the standard Messages API is stateless, so you must always send the full conversational history (Using the Messages API; a beta feature can store history on the server, but those tokens are still input). Each turn's input is all the previous history plus the new message, and the output becomes part of the next turn's input (Context windows). Tool results join the history too, so they count toward the window.

Two ways to trim that history, both used in the demo: clearing drops old tool results, and compaction replaces a long history with a short summary and continues from there (Context windows).

A common mix-up: "the model remembers the earlier steps"

Chat apps feel continuous, and the loop you traced reads like one ongoing thought, so it seems each step only needs the newest message. If the program really sent only the newest message, the model would not even know what the student asked. The program does the remembering, by resending the history every call (Using the Messages API). The model does not.

Two consequences follow. The context grows with each step, and because earlier tokens are billed again as input each time, the total cost grows faster than the number of steps. Try it in the demo.

Between sessions: notes as memory O3 4.5 min

When a session ends, the context is gone. Nothing survives into Wednesday unless the program stored it. This is the job of memory in an agent: notes, kept in files or a database outside the context window, that the agent writes and the program saves, then loads again later. Anthropic's memory tool, for example, lets Claude store and retrieve information across conversations in a directory of memory files (Memory tool).

Think of a car's service logbook: the mechanic does not remember your car from last year, the logbook does. Figure 2 shows the same arrangement for Sam.

In the memory tool the model does not touch the disk itself. It requests file operations (view, create, str_replace, insert, delete, rename), and your application runs them against storage you control; the model checks its memory directory before starting a task and saves what it learns under /memories (Memory tool). It is the same loop you already know, with a file tool. An adapted exchange for Sam looks like this:

model:   view /memories
program: training.md
model:   view /memories/training.md
program: laser cutter: trained Monday
         3D printer: not yet trained

The file's content now sits in the Wednesday context as a tool result, a short note instead of Monday's whole transcript. This is the structured note-taking Anthropic describes: the agent writes notes outside the context window and reloads them later, such as a to-do list or a NOTES.md file (Effective context engineering for AI agents).

A common mix-up: "memory means the model learns"

Chatbots say "I'll remember that", so it seems the model changes. It does not. The window is a "working memory" distinct from training (Context windows), so nothing written to memory changes the model, and the memory tool is client-side, run by your application (Memory tool). What looks like learning is a note the program loaded into a new context.

A second mix-up: "save the whole transcript"

It sounds safest, since nothing is lost. But loading it back refills the window, costs tokens and buries the signal, which brings back context rot. The documented pattern is curated: a progress log and a checklist written at the end of each session and read at the start of the next (Memory tool).

What to save is your design choice, and so is what not to save. Expiration, size caps and keeping sensitive data out of memory are the developer's job (Memory tool); for a student record that matters. Memory also pairs with compaction: compaction shrinks the active context, and memory keeps what must survive the summarising (Memory tool).

Retrieval: finding the right page in a long manual O3 5 min

Memory handles what the assistant learned about Sam. The manuals are a different problem: far too long to paste in every time, and mostly irrelevant to any single question. Retrieval means keeping the manual outside the context, and putting in only the few passages that match the question. Think of the index at the back of a service manual: you do not read the whole book to find the torque spec.

In basic retrieval-augmented generation (RAG), the documents are split into small chunks and each chunk is turned into an embedding, a list of numbers that captures its meaning. The embeddings are stored in a database that supports similarity search, and at query time the closest chunks are found and added to the prompt (Contextual Retrieval). Figure 3 shows the path.

Meaning-based matching and exact-word matching fail in different ways, so good pipelines use both: BM25, a keyword method that scores exact word overlap, and embeddings for meaning, with the results merged. Anthropic measured that adding context to each chunk cut the failure rate of finding the right chunk in the top 20 from 5.7% to 3.7%, and to 2.9% with BM25 added (Contextual Retrieval); these are Anthropic's own measurements on their test sets. Chunks can also lose their context: a chunk that does not say which machine it concerns is hard to retrieve or use (Contextual Retrieval).

Retrieval need not be a fixed pipeline. In "just-in-time" retrieval the agent holds light references, such as file paths and queries, and loads content with tools at run time; file names and folders help it judge what is relevant. The trade-off is that run-time exploration is slower and needs guidance, so a hybrid works: preload some context, explore as needed (Effective context engineering for AI agents). Either way, what comes back arrives as a tool result, so it joins the history and counts against the window, which is the previous section again.

For a small knowledge base, Anthropic says you can skip retrieval: under about 200,000 tokens (about 500 pages) you can put the whole thing in the prompt (Contextual Retrieval). Context rot and cost still argue for selecting.
A common mix-up: "retrieval matches the words you typed"

A search box works on keywords, so it is tempting to think the question must use the manual's own wording, or that the model has read the whole manual. Neither is true. Embeddings match by meaning and BM25 by exact words, and only the few top chunks reach the model. A student asking "why does my cut come out burnt?" can still land on a section titled "Power and speed settings for wood", because the meanings are close. But an exact error code like E42 is what exact-word matching is for (Contextual Retrieval).

Worked example and practice: design the assistant's memory O3 5 min

Now put the three together. For each piece of information, ask: does it go in the context for this request, in memory for next time, or in retrieval on demand? All token numbers here are illustrative.

Worked example

Sam asks: "Can I use the laser cutter Friday, and what power for 3 mm acrylic?"

  1. Always in context: the system prompt and tool definitions (about 2,000 tokens) and Sam's question (about 100). Every call needs them, and they are in every call's bill.
  2. Memory, loaded at session start: Sam's training file (about 50 tokens), because the assistant must know Sam is trained on the laser cutter before booking. It is small, curated and saved from last time. The program can preload it, or the model can view it as its first tool call, which puts it in from call 2.
  3. Tool result, then trimmed: the Friday calendar (about 3,000 tokens). It is needed to answer, but after that its raw content can be cleared from later calls.
  4. Retrieval, on demand: the acrylic settings, fetched as a few chunks (about 1,500 tokens) from manuals totalling about 300k tokens, which stay outside.
  5. Saved at the end, if it matters: a booking made and any new training. Not the whole conversation.

Add up the cost of that worked example, since cost is part of your brief. Assume the program preloads the training file, so the loop has three calls:

1fixed 2,000 + question 100 + training file 502,150
2call 1 + request 100 + calendar result 3,0005,250
3call 2 + request 100 + manual chunks 1,5006,850

Each call pays again for everything before it. Clearing the calendar result after call 2 would cut call 3 to about 3,850, which is why you retrieve a few chunks rather than many and trim what is settled. Notice too what the design did not do: it did not paste 300k tokens of manuals into the window, and it did not reload Monday's transcript. At the design review that is your argument: every item is placed on purpose, with a reason you can state in one sentence.

A rule of thumb for sorting, in order:

  • Does the model need it on every call of this request? Keep it in context.
  • Will a future session need it? Save a short note in memory.
  • Is it a large body of text where only a small part matters per question? Retrieve it.

Summary O3 1.5 min

  • The context window is everything the model gets for one call, including its own output. It is finite, bigger is not better (context rot), and you pay for it as input.
  • Between steps the model keeps nothing. The program resends the full history every call, so context and cost grow until you clear or compact.
  • Between sessions only saved notes survive. Memory is curated notes the program stores and reloads; the model learns nothing.
  • Retrieval keeps a long manual outside the context and puts in only the best few chunks, which then count against the window.

Say it in your own words: without looking, explain where Sam's training status, the Friday calendar result and the acrylic settings each live, and why.

A model answer

Training status lives in saved memory and is loaded at session start. The calendar result is a tool result in this session's context, cleared when no longer needed. The acrylic settings live in the manual, outside the context, and are retrieved as a few chunks when asked.
