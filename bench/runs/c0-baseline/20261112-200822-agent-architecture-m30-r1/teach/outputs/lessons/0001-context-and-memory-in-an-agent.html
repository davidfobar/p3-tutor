Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in saved notes, or in a manual you search on demand, and give a reason.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small budget. Both problems are context and memory problems. At your design review, "what does the model see at each step, and what survives until next week?" is a question you should be able to answer in one minute.

Warm-up 2 min

Recall

Your assistant gets "Is the laser cutter free on Friday?" and decides to use check_calendar. Who actually runs the tool: the model or the program around it? And what happens to the result?

Check your answer

The model only writes a request naming the tool and its arguments. The program runs the tool, then sends the result back to the model and calls it again. That last part is today's topic: "sends the result back" means the result is added to what the model reads next. We will look at exactly what that pile of text is, how it grows, and what happens to it when the conversation ends.

What the model sees: the context window 4 min

Start with a concrete case. A student types: "Can I use the laser cutter for 3 mm acrylic?" Before the model writes a single word, the program assembles a block of text for it to read. It holds the assistant's instructions (the system prompt), the descriptions of the three tools, and the student's question. That is everything the model knows about this request. It cannot see the booking system, last week's chat, or the manual PDF unless the text is in that block.

That block is the context: the tokens given to the model when it generates its next output (Anthropic, "Effective context engineering for AI agents"). A token is a small chunk of text, often a short word or a piece of a longer one. The context window is the limit on how much the model can look at at once. Anthropic's documentation defines it as all the text the model can reference when generating a response, including the response itself, and calls it the model's working memory, which is different from the data it was trained on (Claude docs: Context windows).

Everything counts toward the window: the system prompt, every message, every tool result, the tool definitions, and the model's own output. The docs list all of these. A common surprise is that tool definitions count. If you write ten tools with long descriptions, you pay for them in every single call.

A common mix-up

"The model remembers our earlier chats." It is tempting because chat apps feel like talking to someone who knows you. But the model itself holds nothing between calls. Each call starts from the text it is given. A chat app creates the feeling of memory by re-sending the earlier conversation each time. When your program calls the model, you decide what is re-sent. If you send nothing from last week, the model knows nothing from last week.

Check yourself

The assistant's Python program calls the model once for a new student. The student's training status is stored in a database, but the program does not put it into the text it sends. What does the model know about that student's training?

Show the answer

Nothing. The model knows only what is in its context, and the program never put the status there.

Between steps: the context grows 5 min

Now the agent loop from your last session, seen from the model's side. Every step is a separate model call, and the program builds the context for each call from scratch. In an agent loop it does this by appending: the original question, then the model's tool request, then the tool's result, then the next request, and so on. Anthropic's context-engineering post puts it this way: in a loop, the agent generates more data that could be relevant on every turn, and it has to be refined (Anthropic).

Here is the laser-cutter question, step by step. The token counts are made up, to show the shape; real counts depend on your prompt and manuals.

CallNew text addedContext size
1System prompt (800), tool descriptions (700), question (30)1,530
2Model's request for search_manuals (40), manual pages returned (3,000)4,570
3Model's request for check_calendar (40), calendar result (200)4,810
4Final answer (150)4,960 at the end

Notice two things. First, the manual pages added in call 2 are still in the context in calls 3 and 4, even though the model has already used them. Nothing removes them unless you decide so. Second, each call reads the whole context again. Counting only what the model reads (the context before each call), the four calls read about 1,530 + 4,570 + 4,810 = 10,910 tokens, not 4,960. Model usage is billed by tokens, so a long loop with a big early tool result pays for that result again at every later step. Prompt caching can make a repeated prefix cheaper, but the docs are clear that cached tokens still occupy the window (Claude docs). So caching changes what you pay, not how much fits.

Size also affects quality, not just cost. The docs state that as token count grows, accuracy and recall degrade, a phenomenon called context rot, and that more context is not automatically better (Claude docs). Anthropic's engineers describe an "attention budget" that every added token uses up, and they say the decline is a gradient, not a cliff (Anthropic). Their goal is the smallest set of high-signal tokens that gets the result you want.

A common mix-up

"A bigger context window means I can just put everything in." It is tempting because some current models accept up to a million tokens, enough for many manuals at once. But a window is a limit, not a target. Everything you put in is re-read and paid for on every call, and it can make the model less accurate on the one page that matters. A big window gives you room; you still have to choose what goes in it.

Check yourself

An agent run has a 6,000-token tool result in its context after step 2, and finishes at step 5. Roughly how many times does the model read that result?

Show the answer

Three times. The result arrives after the step-2 call, so the calls at steps 3, 4 and 5 each read it again.

Keeping the context small 4 min

If the context grows with every step, the program has to manage it. Three ideas from the sources are enough for a first design.

1. Return less in the first place

The cheapest context is text that never enters. Instead of a tool that returns a whole 40-page manual, return the three most relevant paragraphs. This is a design choice in your tool, and it comes before any clever trick. Anthropic's advice on tools is to make them token-efficient (Anthropic).

2. Clear old tool results

Once the model has used a tool result, an old copy is rarely needed. Anthropic calls tool result clearing one of the safest, lightest forms of compaction: delete the bulky result deep in the history, and keep the record that the call happened. If the model needs the text again, it can call the tool again (Anthropic). In our table, this would drop the 3,000 manual tokens before call 4.

3. Compaction

Compaction means that when a conversation nears the window's limit, the program has the model summarise it, then starts a fresh context with that summary. Claude Code, for example, keeps the summary plus the five most recently accessed files. The post advises tuning compaction to keep important details first, then trimming extras (Anthropic). The Claude docs describe server-side compaction as the primary strategy for long-running agent work (Claude docs).

For your assistant, most requests are short: a few tool calls. You probably need idea 1 and maybe idea 2. Compaction matters for long sessions, such as a student chatting for an hour about a project.
Check yourself

search_manuals returns the full text of a 40-page manual (about 30,000 tokens) on every call. Which change helps most, and first?

Show the answer

Make the tool return only the relevant paragraphs. It removes the cost at the source.

Between sessions: notes as memory 5 min

Everything so far lives and dies inside one run. When the run ends, or the context is reset or compacted, it is gone. Now the second problem: Maya trains on the laser cutter on Monday. On Thursday she opens a new chat. The assistant should know she is trained.

Since the model keeps nothing, memory in an agent means information the program saves outside the context window and puts back when needed. The simplest form is notes. Anthropic calls it structured note-taking: the agent writes notes to storage outside the context window and pulls them back in later, like a NOTES.md file or a to-do list (Anthropic).

Anthropic's memory tool is a ready-made version. It lets the model store and retrieve information across conversations in a directory of files, and it works like any other tool from the last lesson. The model writes a request such as "create a file /memories/maya.md with this text". The program runs it against storage you control, whether a disk, database or cloud store, and returns the result. The model never touches storage itself. The tool offers commands to view, create, edit, rename and delete files (Claude docs: Memory tool).

Two things make notes work. Read first: the memory tool's instructions have Claude check the memory directory before starting a task, and warn that "your context window might be reset at any moment," so progress should be saved as it goes. Write before you stop: in the docs' multisession pattern, each session reads a progress log first and updates it before ending (Claude docs: Memory tool). The docs also advise validating every file path (so a request cannot escape the memory folder), limiting file sizes and deleting files that are not accessed for a long time.

A design point for you: notes are data about real students. Training status should come from your authoritative records, not from whatever the model decided to write down. A good split is that the program reads the training record at the start of a session and puts one line into the context, while free-form notes hold softer things, like "prefers evening slots".

A common mix-up

"Turn on memory and the assistant just remembers." It is tempting because products advertise it that way. In your code, memory is a design you build: what gets written, where it is stored, when it is read back, and when it is deleted. Without the read step, a perfect notes store does nothing.

Check yourself

Session 2 starts and the model's first action is to view /memories. Which is the best description of why?

Show the answer

Its context starts empty, so it reads the notes to bring the past back in.

Retrieval: finding the right page 3 min

Notes solve "remember Maya." They do not solve "find the right page in a 300-page laser cutter manual." That is retrieval: fetching just the relevant pieces of a large body of text into the context when they are needed, instead of loading all of it.

Anthropic describes the approach as just-in-time. The agent holds lightweight references such as file paths, search queries and links, and loads the data with tools at the moment it needs it (Anthropic). Their trade-off is honest: this is slower than having everything ready, and exploring can waste context if the agent searches badly. Claude Code mixes both. Some files go in up front, and the rest are found with search tools as needed.

For your manuals, a simple retrieval design looks like this:

  1. Prepare once: split each manual into small pieces, such as one section or a few paragraphs, and label each with its machine and section title.
  2. Search on demand: search_manuals(machine, query) finds the best few pieces for the query, by keyword match or another scoring method.
  3. Return little: the tool returns those pieces, with their titles so the answer can cite them.

Notice that retrieval is the same tool loop you already know. The "memory" here is a tool result that enters the context for a while. It is also the idea behind Section 3: return less in the first place. Choosing how to split and search is where the quality of your assistant will be won or lost, and it is cheap to test with a list of ten real student questions.

The memory tool from Section 4 and a manual search tool look alike to the model: both are tools it can call to read stored text. The difference is who put the text there. Notes are what the agent wrote itself earlier; the manuals are source material you prepared.

Worked example and practice 5 min

Now use the three places together. Each fact has a home: context (for this run only), notes (kept between sessions) or retrieval (stored source material, searched when needed).

Question to ask about a factIf yes
Does the model need it on every request, and is it short?Context (system prompt)

Worked example

Place four facts for the assistant: (A) "Always cite the manual section you used." (B) "Maya completed laser cutter training on Monday." (C) The 3D printer's nozzle-cleaning procedure, page 41. (D) The calendar result "Laser cutter: Friday 2-4 pm free".

  1. A: short, needed on every request, same for every student. It goes in the system prompt, so it is part of the context in every call. It costs a few tokens each time, which is fine.
  2. B: about one student and needed on Thursday, when this run's context is long gone. It goes in notes (or, better, the training record the program reads at session start), and the program reads it into the context when Maya's session begins.
  3. C: one page of a large shared manual, needed only when someone asks about nozzles. It stays in the manual store, and retrieval brings it into the context when asked. Putting every procedure in the system prompt would be re-read on every call for no reason.
  4. D: a result for this question. It enters the context as a tool result and helps the model answer. It does not belong in notes: tomorrow the calendar will have changed, so a saved copy would go stale. After the answer, it can be cleared.
Your turn

Place these three facts, with a reason for each: (E) "Students under 18 need a staff member present." (F) Jon asked last week not to be booked before 10 am. (G) The laser cutter's 12-page safety manual. The first step is given: for E, ask whether it is short and needed on every request.

Show a solution

E: short, needed on every request and the same for everyone, so it goes in the system prompt (context). F: about one student, needed in a later session, so it goes in notes, read when Jon's session starts. G: large, shared, and needed only for some questions, so it goes in retrieval. Twelve pages is smaller than the full manual, but putting it in every call would still be re-read and paid for each time. If your design review pushes back that this is a lot of design for three facts, the reply is the budget: every fact in the context costs tokens on every call.

Summary 2 min

  • The context is all the text the model sees in a call; the context window limits it. The model remembers nothing outside it.
  • In an agent loop the context grows at every step, and each call re-reads all of it. That costs tokens and can lower accuracy (context rot).
  • To keep it small: return less from tools, clear old tool results, and compact when a long run nears the limit.
  • Between sessions, memory is information your program saves outside the window (notes) and reads back at the start.
  • Retrieval brings in only the relevant pieces of a large text, just in time, through a tool.

Say it in your own words: without looking, explain to a teammate why the assistant needs both notes and retrieval, and what each one stores.
