Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in a saved note, or in a manual you search on demand.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small budget. Both jobs come down to one question: what does the model see at each step, and what is saved elsewhere? This lesson gives you the vocabulary and the rules of thumb to defend your answer at the design review.

The context window: what the model sees 6 min

Start with a concrete case. A student types, “What speed should I use to cut 6 mm acrylic on the laser cutter?” Before the model writes a single word, the program builds one long piece of text and hands it over. It contains:

  • the system prompt: your standing instructions (“You are the makerspace assistant. Be brief. Never book a machine without confirming.”);
  • the tool descriptions: the name, purpose and parameters of each tool;
  • the conversation so far: the student's messages and the assistant's replies;
  • any tool results that have come back.

All of that, together, is the model's context: the set of tokens the model is given when it writes its next output (Anthropic, “Effective context engineering for AI agents”). A token is a small chunk of text, roughly a short word or part of a word; the model reads and writes in tokens, and you pay per token. The context window is the maximum number of tokens the model can take in one call. Nothing outside the window exists for the model.

Two facts about the window matter for your budget and your design.

First, you pay for what you put in. Cost is counted in tokens, input and output. A bigger context is a more expensive call. The system prompt and tool descriptions are in every call, so a 2,000-token prompt costs you 2,000 input tokens on every single step of every request.

Second, more is not better. Anthropic's engineering team describes context as “a finite resource with diminishing marginal returns”. They report that as the number of tokens grows, the model's ability to accurately recall information from the context decreases, an effect often called context rot. It is a gradual decline, not a cliff, and it shows up in all models (same source). Their guideline is to find the smallest set of high-signal tokens that gets the result you want.

A common mix-up

“A bigger context window means I can paste in all the manuals and be done.” It is tempting because the window limit sounds like the only constraint. But a window big enough to hold the manuals still bills you for every token on every call, and the model recalls a crowded context less reliably. Fit is not the same as useful. A 300-page manual set in the context to answer one question about the laser's speed settings is expensive and likely to be less accurate than the two relevant pages.

What is kept between steps 5 min

In the agent loop, each step is a separate call to the model. The model does not carry anything over from one call to the next by itself. So how does it “remember” that it just checked the calendar? Because the program puts the earlier steps into the next call's context. The agent's short-term memory is simply the context, rebuilt each step with new material appended.

Worked example: one request, four calls

Student: “Is the laser cutter free tomorrow at 3 pm, and do I need training?”

  1. Call 1. Context: system prompt, tools, the question. Output: request for check_calendar. About 1,800 tokens in.
  2. Call 2. Context: all of the above plus the calendar result. Output: request for search_manuals. About 2,000 tokens in.
  3. Call 3. Context: all of the above plus three pages of manual text. Output: request for check_training_record. About 3,500 tokens in.
  4. Call 4. Context: everything so far plus the training result. Output: the final answer. About 3,700 tokens in.

Total input is about 11,000 tokens, though the new information was only about 2,000. Each call re-reads everything before it.

This explains a cost fact that surprises people: a loop of N steps costs more than N times one call, because later calls are larger. It also shows where the pressure comes from: tool results. A manual search that returns five full pages adds thousands of tokens to this and every later call.

Long tasks eventually threaten the window limit. Anthropic describes compaction: when the conversation nears the limit, summarize it and start a fresh window with the summary, keeping decisions and open problems and dropping redundant tool output. They call clearing old tool results the “lightest touch” form of it (Anthropic). For your assistant, most requests are short, so the simplest version is enough: once the answer from search_manuals has been used, you do not need to keep all three pages in later calls.

What is kept between sessions: notes 6 min

A session is one conversation, from first message to last. When it ends, the context is gone. Next week, when the same student returns, a new session starts with only the system prompt and tools. The model does not know the student, their training, or what you discussed.

A common mix-up

“The assistant remembers earlier conversations automatically.” This is tempting because chatbot products you use appear to remember you. But that is a feature someone built on top of the model: saved text that is loaded into the context. The model alone remembers nothing from one session to the next. If your assistant should remember that Sam passed laser-cutter training, you must store that fact and load it back.

The fix is notes, or external memory: information the program saves outside the context window, in a file or database, and reads back when needed. Anthropic calls this structured note-taking, or agentic memory: the agent writes notes to storage outside the context window and pulls them back in later. Their examples include a to-do list in Claude Code and a NOTES.md file, and an agent playing Pokémon that keeps tallies and maps of what it has explored and reads them after its context is reset (Anthropic). It is the same idea as your own NOTES.md in this workspace, where I keep what you know between our sessions.

For your assistant, think in terms of what to keep:

InformationKeep it?Where
Student's training status (“laser: passed, March”)Yes, between visitsA record keyed by student ID, loaded at session start
Preferred machine or usual booking timesMaybe; small and usefulSame record, one short line
The full chat transcript of every visitUsually noCostly to reload and mostly noise
Today's calendarNoAsk the tool again; it changes

Two rules follow. Save facts, not transcripts: a short note costs a few dozen tokens each time it is loaded; a transcript costs thousands. And do not save what a tool can tell you fresh: a saved calendar goes stale, and a stale fact stated with confidence is exactly the failure you noticed in chatbots. Training status is different because it is your own record of something that does not change by itself.

One caution: the program decides what is written and when. If the model can write notes through a tool, give it a clear tool description and keep the notes short, or the memory itself becomes a pile of tokens that you pay for in every future session.

Retrieval: finding the right page 6 min

The same idea answers your other design question: how does the assistant answer from a long manual? It cannot hold the manual in the context at reasonable cost, so it keeps the manual outside and brings in only the part it needs. Retrieval means searching a store of documents for the pieces relevant to a question and putting those pieces into the context. Anthropic's guide to building agents lists retrieval, tools and memory as the three augmentations of a basic model call (Anthropic, “Building effective agents”).

Take the question: “What feed rate for 6 mm acrylic?” The usual steps are:

  1. Before the system goes live, split each manual into chunks, pieces of a few paragraphs each, and index them so they can be searched.
  2. At question time, search the index and take the top few chunks.
  3. Put those chunks into the context, as a tool result, and let the model write the answer from them.

Search can be by keywords (good for exact things like “E-14 error” or a part number) or by meaning, using embeddings, numeric fingerprints of text that put similar meanings close together (good for “why does it smell burnt?” matching a page about overheating). Many systems combine both. Chunking has a weak point: a chunk cut from the middle of a manual can lose what it is about. A chunk saying “set it to 40%” does not say which machine or material. Anthropic's contextual retrieval technique adds a short, model-written description of where the chunk comes from to each chunk before indexing, and reports fewer retrieval failures (see the sources below; I only read secondary summaries of the numbers, so check them in the original). A cheap alternative for your manuals: put the machine and section name at the top of every chunk yourself.

Up front, or on demand?

You have two ways to run retrieval. In up-front retrieval, the program searches once, before the model runs, and puts the results in the context. In just-in-time retrieval, the model gets a search tool and decides when to call it and with what query. Anthropic describes agents that keep lightweight references (file paths, stored queries, links) and load the data at run time with tools; Claude Code is a mix, loading some files up front and fetching others as needed. The trade-off they note is that run-time exploration is slower, and needs good tools or the agent can waste context (Anthropic).

For you, search_manuals as a tool is the just-in-time option: the model decides a manual search is needed, as in your four-call example, and a question like “is the laser free tomorrow?” skips it entirely, which saves tokens.

A common mix-up

“Retrieval means the model reads the whole manual and picks out the answer.” It is tempting because that is how a person looks something up. But the model only ever sees the chunks the search returned. If the search misses the right page, the model never sees it, and it may answer from the wrong page or from its general training. Most wrong answers from a retrieval system are a failed search, not a failed model, so test the search on its own: for twenty real student questions, does the right chunk appear in the top five?

Worked example and practice 5 min

Worked example: sorting the information

For the assistant, decide for each item: always in context, saved notes, or retrieved on demand. Item: “The rule that students under 18 need a staff member present.”

  1. How often is it needed? Rarely, only for questions about age or access. Not worth 50 tokens on every call.
  2. Does it change per student? No, it is a general rule. So it is not a per-student note.
  3. Is it findable by search? Yes, it sits in the makerspace policy document.
  4. Decision: retrieved on demand from the policy document. Compare “Never book a machine without confirming”, which applies to every request: that goes in the system prompt.

Summary 2 min

  • The context window is everything the model sees in one call, and it is limited and billed by the token; more is not better.
  • Between steps, memory is the context itself, resent and growing with each call; tool results are the main source of growth.
  • Between sessions, nothing survives unless saved as notes and loaded back: save short durable facts, not transcripts.
  • Retrieval keeps long documents outside the context and brings in only the relevant chunks; when answers are wrong, check the search first.
