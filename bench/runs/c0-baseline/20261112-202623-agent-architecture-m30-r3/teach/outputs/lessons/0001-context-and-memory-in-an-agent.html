Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what goes in the model's context at each step, what gets saved between visits, and how it finds the right page in a long manual.

Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Both jobs are memory problems, and both cost money. At your design review, "what does it keep, and why?" will be asked, and this lesson gives you the answer.

Check your answer

The context window: all the model sees 6 min

Start with an example

A student types: "Is the laser cutter free Friday at 3, and do I need training?" Your program does not just send that sentence. It sends a bundle:

  1. the system prompt: your instructions ("You are the makerspace assistant. Be brief. Never book without confirming."),
  2. the tool definitions: the name, description and parameters of each tool,
  3. the messages so far: the student's question and, as the loop runs, every tool request and every tool result.

All of that, together with the reply the model writes, is the context window. The Claude documentation puts it this way: it is "all the text a language model can reference when generating a response, including the response itself", and it is a "working memory" for the model, different from the large corpus the model was trained on (Claude docs: context windows). The docs also say everything in the request counts toward it, including the system prompt, the tool results and the tool definitions.

Text is measured in tokens: small chunks of text, a bit shorter than a word on average. A model's window has a maximum number of tokens. Some current models go up to a million, but the limit is not the main problem, as the next section shows.

The model has no memory of its own

Here is the idea that everything else rests on. The model does not remember the previous step. Each call starts blank, and the program re-sends the whole history. The docs describe it: each turn's input "contains all previous conversation history plus the current user message", and the output "becomes part of the input for the next turn."

A common mix-up

"The model learns from the conversation and remembers it." It is tempting because chatbots seem to remember you. But the model's training is finished; chatting with it does not change it. Whatever "remembering" you see is the program re-sending earlier text. If the program does not send it, the model does not have it. This is also why memory between visits is not automatic: it is something you build.

Why a growing context costs money 5 min

You said the budget is small. Here is where it goes. Usage is billed by tokens, and each call sends the whole context again, so the same text is paid for on every call (prompt caching can lower the price of repeated text, but the docs say it "changes what you pay for those tokens, not whether they count" toward the window; see Claude docs: context windows).

Worked example: counting input tokens

The makerspace request from above. Assumed sizes: instructions plus tool definitions 2,000 tokens; the question 100. Each tool request the model writes is about 50 tokens. Results: the calendar 400, the manual search 3,000, the training record 150. The model calls three tools and then answers.

  1. Call 1 sends 2,000 + 100 = 2,100 tokens. The model requests the calendar.
  2. Call 2 sends call 1's input, plus the 50-token request, plus the 400-token result: 2,100 + 50 + 400 = 2,550. The model requests a manual search.
  3. Call 3 sends 2,550 + 50 + 3,000 = 5,600. The model requests the training record.
  4. Call 4 sends 5,600 + 50 + 150 = 5,800. The model writes the answer.
  5. Total input over the request: 2,100 + 2,550 + 5,600 + 5,800 = 16,050 tokens, though the whole conversation holds only about 5,800 tokens of text.

Notice that the 3,000-token manual result is paid for in call 3 and call 4. One big tool result is expensive twice.

There is a second cost besides money: quality. Anthropic's engineers describe context rot: as the number of tokens in the window grows, the model's ability to accurately recall information from it decreases. They treat context as "a finite resource with diminishing marginal returns" and say the aim is "the smallest possible set of high-signal tokens" that gets the result you want (Anthropic: effective context engineering for AI agents). The Claude docs say the same: as token count grows, accuracy and recall degrade.

A common mix-up

"A bigger window means we can paste in all the manuals and skip the rest." It is tempting, because a bigger window sounds like a bigger brain. But a window is room, not skill: every pasted page is re-sent and billed on every call, and more text can mean worse recall of the one page that matters. Fit is not the same as a good design.

Between steps: keep, clear, compact 5 min

Inside one request the program decides what to put in the next call. The default is to keep everything, as in Figure 1. Long runs need choices. Anthropic describes three:

  • Clearing old tool results. Once the model has used a result, the raw text can often be dropped. The article calls this "one of the safest lightest touch forms of compaction."
  • Compaction: summarize the history, then start a new context window with the summary, keeping what matters such as decisions and unresolved problems.
  • Sub-agents with clean windows. A helper does a focused job in its own window and hands back a short summary, often 1,000 to 2,000 tokens. You will meet this in a later lesson on multi-agent design.

All three come from Anthropic's context engineering article.

Example. After the assistant has read the laser-cutter manual page and extracted "Acrylic up to 6 mm; no PVC", the 3,000-token page can be replaced by that one line. Call 4 in the worked example drops from 5,800 to about 2,850 tokens. The risk: if you drop something the model needs later, it is gone. Clear what is finished, keep what is pending.

For a makerspace question, one request is short: a few tool calls. You will probably need little compaction. It matters for long sessions, such as a student talking to the assistant for an hour.

Between sessions: notes 5 min

When the student closes the chat, the context window is gone. Next week's session starts blank. Whatever must survive, such as "Riley finished laser cutter training on 3 March", has to be written somewhere outside the window and loaded back in.

Anthropic calls this structured note-taking, or agentic memory: the agent "regularly writes notes persisted to memory outside of the context window", and pulls them back in later (same article). Its example is an agent playing Pokémon that keeps tallies and maps across thousands of steps and reads its own notes after the context resets. Another is a plain NOTES.md file.

For your assistant, think of two kinds of saved information:

KindExampleWho writes it
Facts your system ownsTraining status, bookingsYour tools and database, not the model's guess
Notes the model keeps"Prefers morning slots"The model, through a tool such as save_note

Training status is safety-relevant, so it should come from a record that your own code updates, and the assistant should read it through a tool. Notes the model writes are fine for soft preferences, but the model can note something wrong, so keep them short and separate.

Loading is a design choice too. Load a small summary at the start of each session, and let the model call a tool for details. Loading every old note at the start repeats the cost problem from earlier.

Retrieval: finding the right page 5 min

The manuals are too long to put in the window (and you now know why you would not want to). So the assistant needs retrieval: finding the few passages that matter for this question and putting only those in the context.

Example. The student asks, "What speed do I use to cut 3 mm plywood?" The program has split every manual into chunks of a few paragraphs. A search tool scores the chunks against the question and returns the top three. Those three chunks, maybe 600 tokens, enter the context instead of a 40-page manual at 30,000.

How does the tool score chunks? Two common ways, often combined. Keyword search (such as BM25) matches exact words, which is good for a part number like "RD-6040". Embedding search turns text into numbers so that chunks with a similar meaning score close to the question even with different words, which is good for "how fast should I cut thin wood". Anthropic's research found that combining the two, and adding context to each chunk, cut failed retrievals substantially in their tests (Anthropic: Contextual Retrieval). One of their points is useful for you: a chunk like "set it to 40" loses meaning when separated from its manual, so tag each chunk with its machine and section.

Two ways to wire retrieval in

  • Up front: the program searches before the first model call and places the results in the context.
  • Just in time: the model gets a search_manuals tool and decides when to call it, loading data only as needed. Anthropic describes agents that keep lightweight references and load data at runtime with tools, and notes the trade-off that this is slower and needs good tool guidance (Anthropic).

For the makerspace, just-in-time fits: the assistant must handle manual questions, calendar questions and booking in one conversation, and only some questions need the manuals. Notice that retrieval is also memory, in this sense: the manuals are a long-term store the model reads from, one small piece at a time.

Worked example and practice 5 min

Worked example: sorting what the assistant needs

Sort four pieces of information into: always in context, retrieved when needed, saved between sessions.

  1. "Be brief; confirm before booking." Needed on every call, and short. It goes in the system prompt, always in context.
  2. The band-saw manual. Long and needed only for some questions. Retrieved with a search tool, in small chunks.
  3. A student's finished training courses. Needed in a later visit and safety-relevant. Saved in a record your code controls, read through a tool.
  4. The tool definitions. Needed so the model can call tools at all. Always in context, so keep descriptions short, since they are paid for on every call.

Rule of thumb: ask "needed every call?", then "too long to include always?", then "must it outlive this session?".

(c) The note "Riley's session last week ended before the booking was confirmed." Step 1 is given: (a) is short and needed on every booking, so it is always in context. (b) Too long to include always and needed only for some questions, so retrieve it in chunks with a search tool. (c) It matters in a later session, so it must be saved outside the window; load a short version at the start of the next session, or let the model fetch it with a tool.

Your turn: cost

Instructions and tool definitions are 1,500 tokens, the question 100. The model calls tool A (request 50 tokens, result 200) and then tool B (request 50, result 2,000), then answers. Using the method of the worked example, what is the total input over the three calls?

Show a solution

Call 1: 1,500 + 100 = 1,600. Call 2: 1,600 + 50 + 200 = 1,850. Call 3: 1,850 + 50 + 2,000 = 3,900. Total: 1,600 + 1,850 + 3,900 = 7,350 tokens.

Summary 2 min

  • The model has no memory of its own. The context window, the text the program sends in each call, is all it sees.
  • Within a request, context grows with every tool result, and you pay for the whole of it on every call. Keep it small by trimming tool results, clearing finished ones and compacting long histories.
  • Between sessions, only what you save outside the window survives. Facts that matter, like training status, should live in a record your code controls.
  • Retrieval puts a few matching chunks of a long manual in the context, rather than the whole manual.
