Warm-up 2 min

Recall

From memory: in the agent loop, who actually runs a tool such as check_calendar, the model or the program around it? And what happens to the result?

Check your answer

The program runs the tool. The model only writes a request that names the tool and its arguments. The program then sends the result back to the model as new text, and the model is called again. That last part matters today: the result becomes part of what the model sees on the next call, and the sum of everything it sees is its context.

The context window 5 min

Start with a concrete case. A student types: "Is the laser cutter free tomorrow at 3 pm, and do I need training to use it?" Before the model writes a single word, the program assembles the text to send it. That text is the system prompt (the standing instructions, such as "You are the makerspace assistant"), the description of each tool, and the student's question.

Everything the model can see when it writes its next output is called its context. The limit on how much text fits is the context window. Text is counted in tokens, small pieces of text, often a short word or part of a longer word. As a rough guide, a page of a manual is several hundred tokens. The window counts the input and the output together.

Anthropic's documentation describes the context window as the model's "working memory" for a request, and notes that it is not the same thing as the large body of text the model was trained on (Claude docs: context windows). Training shaped what the model knows in general. The context is what it knows about this request. If a fact about the laser cutter is not in the context, the model cannot use it, however good the model is.

Window sizes differ between models and change often, so look up the current number for the model you pick instead of memorising one. The Claude docs page above lists them.

Two consequences follow, and both drive your design.

  • Limit. If the context grows past the window, the request cannot continue as it is. Something has to be dropped or shortened.
  • Cost. You are charged by tokens, and the model reads the whole context on every call. A bigger context makes every call dearer. Section 3 puts numbers on this.

What is kept between steps 5 min

In the agent loop, the model is called once per step. A natural guess is that the model carries on from step to step the way you carry on a thought. It does not. Each call is separate: the model keeps nothing from the previous call inside itself. What looks like continuity is the program sending the whole conversation again.

So the program keeps a list of messages: the question, each tool request the model wrote, and each tool result. On every call, it sends that list (plus the system prompt and tool descriptions) from the top. This growing list is often called the history or the message list. It is the agent's short-term memory, and it lives in your Python program, not in the model.

A common mix-up

"The model remembers what happened earlier in the request." It is tempting because the answers at step 4 clearly use what was found at step 2. But the model sees step 2's result only because your program put it in the list again. If your program forgot to append a tool result, the model would behave as if the tool had never been called, and it might call it again. The memory is in the list you keep.

This is also why the same list is the thing you control. You can add to it, shorten it, or replace old parts with a summary. Anthropic's engineering team calls this kind of work context engineering: deciding which tokens go into the context at each step, as the best set of information for the desired result (Effective context engineering for AI agents).

A full context costs money and accuracy 6 min

Because the whole list is sent on every call, the cost of a request grows faster than you might expect. Here is the laser cutter question again. Assume these sizes (they are made-up round numbers, but the pattern is real):

Worked example: counting what is sent

System prompt 500 tokens, tool descriptions 600, the student's question 30. Each tool request the model writes is 40 tokens. The calendar result is 300 tokens, the manual search returns three pages at 700 tokens each (2,100), and the training record is 150.

  1. Call 1 sends 500 + 600 + 30 = 1,130 tokens. The model writes a 40-token calendar request.
  2. Call 2 sends call 1's input, plus the 40-token request and the 300-token result: 1,130 + 40 + 300 = 1,470.
  3. Call 3 adds another 40-token request and the 2,100-token manual result: 1,470 + 40 + 2,100 = 3,610.
  4. Call 4 adds 40 + 150: 3,610 + 190 = 3,800. The model now writes the final answer.
  5. Total tokens read across the four calls: 1,130 + 1,470 + 3,610 + 3,800 = 10,010, about 2.6 times the final context of 3,800.

You pay for the model to read the early parts again at every step, which is why a long tool result is costly twice over: it is read once when it arrives and again on every later call. Providers also publish prices per token, so the number of tokens read is the number to watch against your sponsor's budget.

There is a second cost, and it is about quality. More context does not simply mean better answers. Anthropic's engineering post describes the model as having a limited "attention budget", and says that as the number of tokens grows, the model's ability to recall information from the context decreases. It recommends the smallest set of high-signal tokens that gives the result you want. A research paper, Lost in the Middle, tested models on questions with long inputs and found they do best when the relevant text is at the start or end, and worse when it sits in the middle, even for models built for long inputs.

A common mix-up

"A bigger context window means I can just put everything in." It is tempting because a big window sounds like a big memory. But a window is a ceiling, not a target. Filling it makes every call dearer and can bury the one sentence the model needs. A larger window raises the limit; it does not fix cost or attention.

When a long-running agent gets close to the limit, there are standard remedies. One is to compact the history: replace old steps with a short summary and keep going. Another is to keep tool results small to begin with, for example by returning three relevant pages, not the whole manual. A third is to write notes outside the context, which is the next section.

Between sessions: notes as memory 5 min

The message list lives while the request runs. When the student closes the chat, your program can throw it away, and the model keeps nothing. The next time the same student arrives, a fresh context starts with only the system prompt and tools. So if the assistant is to know that this student passed the laser cutter training last month, something outside the model must hold that fact and put it back into the context when needed.

That something is external memory: notes saved in a file or a database by your program. It has two halves.

  • Write. When something worth keeping happens, the program or the model (through a tool such as save_note) records it: "Student 4471: passed laser cutter training on 14 Oct."
  • Read. At the start of a later session, or when it becomes relevant, the program loads the right notes into the context.

Anthropic's engineering post calls the agent version of this structured note-taking: the agent writes notes outside the context window and pulls them back in at later times (Effective context engineering for AI agents). The same idea helps inside a long session, since notes survive when old history is compacted away.

Keep notes small and specific. Saving the whole chat transcript just moves the context problem into a file. A short record of facts that will matter next time (training passed, preferred machines, a pending booking) loads cheaply and is easy for the model to use. Also decide what must not be remembered: a note that is wrong or stale will mislead every future session, so notes need a date and a way to be corrected.

Retrieval: finding the right page 5 min

The manuals are the third kind of memory. They are far too long to place in every context, and most pages are irrelevant to any one question. Retrieval means fetching only the few pieces of a large collection that matter for the current question and putting them into the context.

In an agent, retrieval is simply a tool: search_manuals(query). The model writes a query, the program searches, and the matching pages come back as the tool result. Anthropic describes this as just-in-time retrieval: keep lightweight pointers, such as file names, and load the data when it is needed, instead of loading everything up front (Effective context engineering for AI agents).

Two practical steps make it work.

  1. Split the manuals into chunks. A chunk is a section or a few paragraphs, with a label such as "Laser cutter, section 4: Materials". Chunks are small enough to fit several in one result.
  2. Search the chunks. A keyword search finds chunks containing the words the student used. A meaning-based search matches chunks that say the same thing in different words, which helps when a student writes "how thick can I cut" and the manual says "maximum material depth". Many systems use both.

Retrieval can fail in two ways, and both show up as a wrong answer that sounds sure. The right page may not be found, because the chunk was cut badly or the query used different words. Or too many pages come back, which fills the context with noise. Return a small number of chunks, show their labels so the model can say where an answer came from, and test with real student questions.

A common mix-up

"Retrieval makes the model learn the manuals." It is tempting because answers afterwards use the manuals' facts. But the model learns nothing: the retrieved pages are pasted into the context for this call only. On the next call they are present only if your program keeps them in the list. Retrieval is a way of lending the model a page, not teaching it.

Worked example and practice 9 min

Worked example: sorting the assistant's information

For each item, ask three questions in order. Is it needed in this request only? Is it a fact about one student that must outlive the chat? Is it a large shared document where only a part is needed at a time?

  1. The assistant's rules and tone. Needed in every request, short, the same for everyone. It goes in the system prompt, in the context.
  2. The student's question and the tool results so far. Needed only for this request. It lives in the message list and is gone when the session ends.
  3. "Student 4471 passed laser training." A fact about one person that must outlive the chat. It goes in the notes store and is loaded at the start of that student's next session.
  4. The band saw manual. Large, shared, and only one section is needed per question. It goes in the manual store and is reached through search_manuals.

Cost follows the same sorting: only the first two kinds are read at every call, so keep them small.

Summary 2 min

  • The model sees only its context. The context window is the limit on how much fits, and you pay for every token read on every call.
  • Between steps, the program keeps the message list and sends it all again. The model keeps nothing itself.
  • A fuller context costs more and can make the key fact harder to find, so keep it small and high-signal.
  • Between sessions, memory is notes your program saves and reloads. Large shared documents are reached by retrieval, a search tool that returns a few chunks.
